# ts-bin-rpc: дизайн и архитектура

Статус: черновик v0, согласован 2026-11-02. Рабочее имя `ts-bin-rpc` (на npm свободно), CLI `tbr`.
Финальное имя выбирается перед публикацией.

Основания для решений: [исследование](../reports/Обзор%20TS%20RPC%20и%20бинарных%20форматов.md),
[замеры](../README.md), [спайк TS 7.1](../spikes/ts71/).

## 1. Цели и не-цели

**Цели**

1. **Code-first.** Контракт — обычные TS-интерфейсы и роутер из обычных async-функций. Без IDL, без
   схем-валидаторов, без цепочек билдеров.
2. **DX уровня tRPC.** Типы клиента выводятся из `typeof appRouter`: автокомплит, переход к
   определению и переименование работают сквозь клиент и сервер без шага сборки.
3. **Бинарный формат везде.** Ленивые views на клиенте, колонки `TypedArray` без копирования,
   верификация недоверенного входа на сервере.
4. **Эволюция схемы с первого релиза.** Lockfile со стабильными ID полей и проверка совместимости
   в CI.
5. **Работа в любом рантайме и сборщике.** Сервер на Fetch API (Node, Bun, Deno, Workers), клиент —
   обычный `.ts`, который не требует плагинов сборщика.

**Не-цели alpha**

- Паритет с tRPC по экосистеме: TanStack Query, подписки, батчинг, цепочки мидлваров. Это пост-alpha.
- Клиенты на других языках, экспорт в `.fbs` или Arrow.
- Совместимость по байтам с FlatBuffers.
- Победа над `JSON.parse` на строковых данных любой ценой. Цель — паритет по размеру после
  сжатия (см. §11) и выигрыш на числах и частичном чтении.

## 2. Как это выглядит для пользователя

**Типы**

```ts
// shared/types.ts
import type { u32, f32, u64 } from 'ts-bin-rpc';

export interface User {
  id: u32;
  name: string;
  email?: string;
  role: 'admin' | 'user';
  createdAt: Date;
  balance: u64;
}

// Колонки объявляются явно: что объявлено, то и приходит.
export interface Series {
  t: Float64Array;
  value: Float32Array;
}
```

**Сервер**

```ts
// server/router.ts
import type { Ctx } from './ctx';

export const appRouter = {
  user: {
    get: async (input: { id: u32 }, ctx: Ctx): Promise<User> => ctx.db.users.get(input.id),
    list: async (input: { limit: u32; cursor?: string }, ctx: Ctx): Promise<User[]> => ...,
  },
  metrics: {
    series: async (input: { from: Date; to: Date }): Promise<Series> => ...,
  },
};
export type AppRouter = typeof appRouter;

// server/main.ts
import { createHandler } from 'ts-bin-rpc/server';
import { serverProcedures } from './tbr.gen.ts';

const handler = createHandler(appRouter, {
  procedures: serverProcedures,
  prefix: '/rpc',
  context: (req) => ({ db, user: auth(req) }),
});
// Bun.serve({ fetch: handler }) / Deno.serve(handler) / export default { fetch: handler }
// Node: http.createServer(toNodeListener(handler)) из 'ts-bin-rpc/node'
```

**Клиент**

```ts
import { createClient } from 'ts-bin-rpc/client';
import { clientProcedures } from '../server/tbr.gen.ts';
import type { AppRouter } from '../server/router';

// clientProcedures: энкодеры входов и декодеры выходов, остальное бандлер выкидывает
const api = createClient<AppRouter>({ url: '/rpc', procedures: clientProcedures });

const user = await api.user.get({ id: 1 });   // ctx в сигнатуре клиента нет; user: User,
                                              // строки декодируются при первом чтении
const s = await api.metrics.series({ from, to });
uplot.setData([s.t, s.value]);                 // Float64Array/Float32Array поверх ответа, без копирования
```

**Кодоген**

```sh
tbr generate             # src/server/router.ts#appRouter → tbr.lock.json, src/server/tbr.gen.ts
tbr check                # CI: lockfile совместим с текущими типами
tbr decode resp.bin --proc user.get    # --input для тела запроса, --type User для объекта
```

## 3. Архитектура

```
 TS-исходники ──► TypeSource (TS 7.1 API) ──► Schema IR ──► Layout planner ◄──► tbr.lock.json
                                                                │
                                                                ▼
                                                            Emitters
                                         ┌──────────────────────┴──────────────────────┐
                                  generated/client.ts                          generated/server.ts
                                 encoders(in), views(out),              decoders+verifiers(in),
                                 verifiers(out, dev), proc table        encoders(out), proc table
                                         │                                             │
                                         ▼                                             ▼
                              ts-bin-rpc/client  ◄──── HTTP (Fetch) ────►  ts-bin-rpc/server
                                         └────────────── ts-bin-rpc (runtime) ─────────┘
```

**Пакеты**

| Пакет | Содержимое | Зависимости |
|---|---|---|
| `ts-bin-rpc` | runtime кодека (`/runtime`), `/server`, `/client`, `/node`, типы брендов; бинарь `tbr`: generate, check, decode, rename | `typescript@7.1` — необязательная peer-зависимость, нужна только `tbr` |

Один пакет, чтобы версии CLI и рантайма совпадали сами: сгенерированный код и рантайм одной версии.
TypeScript пользователь ставит в devDependencies, поэтому в продакшен-установку компилятор и его
Go-бинарь не попадают. Код CLI (около 100 KB) лежит в `dist/cli` и в бандлы не попадает: клиент и
сервер его не импортируют. В репозитории исходники CLI живут в приватном пакете `packages/cli`
(`@tbr/cli`); сборка `ts-bin-rpc` компилирует их в свой `dist/cli`. До 0.1.0-alpha.1 CLI
публиковался отдельно как `ts-bin-rpc-cli`, этот пакет помечен устаревшим.
Сгенерированные файлы коммитятся. Это переживает смену сборщиков, работает при type stripping в
Node и Bun и не требует CLI в production-сборке.

## 4. Извлечение типов (TypeSource)

Узкий интерфейс поверх TS API, единственное место, которое знает про TypeScript:

```ts
interface TypeSource {
  loadRouter(file: string, exportName: string): RouterNode;   // процедуры с типами in/out
  describe(type: TypeHandle): TypeDescriptor;                 // классификация одного типа
}
```

- Бэкенд alpha — `typescript/sync` из 7.1 (спайк: процедуры извлекаются за ~80 ms, бренды, unions,
  опциональные поля видны). Запросы группируются через `api.batch()` и `.gen`-варианты, кэш по
  id типа.
- Запасной путь — бэкенд на `@typescript/typescript6`, если 7.1 упрётся в баги беты.
- Процедура = свойство роутера с call signature. Вход — тип первого параметра (или `void`), выход —
  аргумент `Promise<T>` возвращаемого типа. Второй параметр — `ctx`, в схему не попадает.
- Вложенные объекты без call signature — namespaces. Имя процедуры — путь через точку: `user.get`.

## 5. Модель типов (Schema IR)

**Бренды** экспортирует runtime:

```ts
declare const tbr: unique symbol;
export type u8  = number & { readonly [tbr]?: 'u8' };
// u16, u32, i8, i16, i32, f32, f64; u64 и i64 — поверх bigint
```

Опциональный символьный ключ не мешает писать `{ id: 1 }` и не всплывает в автокомплите. Бренд
определяется по значению литерала у свойства, ключ которого — символ из пакета `ts-bin-rpc`, а не по
имени алиаса: так он сохраняется через `type UserId = u32`. Диапазон (`-1` в `u32`) типами не
проверить, его проверяет кодировщик (§8).

**Поддерживаемые типы (alpha)**

| TS | IR | На проводе | На клиенте |
|---|---|---|---|
| `boolean` | bool | 1 байт | `boolean` |
| `number` (без бренда) | f64 | 8 байт | `number` |
| `u8`…`i32`, `f32`, `f64` | scalar | 1–8 байт | `number` |
| `u64`, `i64` | scalar64 | 8 байт | `bigint` |
| `string` | string | ссылка → heap | `string`, мемоизация |
| `Date` | timestamp | f64 мс | `Date`, мемоизация |
| `'a' \| 'b'` | enum | u8/u16, индекс из lockfile | литерал |
| `Uint8Array` | bytes | ссылка → heap | `subarray` без копирования |
| `Float32Array` и др. `TypedArray` | column | выровненный блок | `TypedArray` без копирования |
| `T[]` | vector | длина + элементы | настоящий `Array` |
| интерфейс / объектный литерал | table | vtable + поля | view |
| `T \| undefined`, `x?: T` | optional | отсутствие в vtable | `undefined` |
| `T \| null` | nullable | бит null | `null` |
| discriminated union | union | u8-тег + table варианта | view варианта |
| дженерики (`Page<User>`) | инстанс | как table | view |
| рекурсивные типы | table | через ссылки | view |

**Отвергаются с понятной ошибкой:** `any`, `unknown`, функции, классы с методами, `Map`/`Set` и
`Record<string, T>` (пост-alpha), кортежи (пост-alpha), unions без дискриминанта (кроме `null`,
`undefined` и литералов), индексные сигнатуры, `symbol`. Ошибка указывает на файл, строку и путь
поля: `User.meta: type 'unknown' is not serializable`.

Принцип: **что объявлено, то и приходит**. `f32[]` — это массив чисел: на проводе компактно, на
клиенте копия в `Array`. `Float32Array` — это колонка без копирования. Никакой подмены типов, иначе
выведенные типы клиента разойдутся с рантаймом.

## 6. Формат на проводе (v0)

Спецификация — [FORMAT.md](FORMAT.md), зафиксирована фазой 0. Главные решения:

- **Одиночный объект — row table с vtable** (в стиле FlatBuffers): ID поля из lockfile → смещение,
  0 = поля нет. Цена косвенности — 3–18% на полном чтении, эволюция схемы бесплатна.
- **Вектор объектов — колоночный** (в стиле Arrow): по колонке на поле, каталог колонок по ID поля.
  Числовые колонки читаются как `TypedArray`. На строковом CRUD это и единственный найденный способ
  стать меньше JSON после сжатия (на 7–20%), и не медленнее row tables.
- **Строки — в двух блоках на сообщение** (ASCII и UTF-16LE), каждый декодируется одним вызовом
  `TextDecoder`, поля берут `substring`. Это быстрее `JSON.parse` во всех трёх браузерах. Строковые
  колонки хранят длины и обратные ссылки на повторы, а не смещения.
- **Ошибки** кодируются фиксированным конвертом, который читается без схемы процедуры.
- **Struct** (замороженная раскладка без vtable) — пост-alpha.

Итог по скорости в браузерах (1000 юзеров, относительно `JSON.parse(bytes)`): полное чтение в
2.4–3.1 раза быстрее, частичное — в 4.2–8.2 раза, кодирование — в 1.5–2.1 раза
([layout.md](../bench/results/layout.md)).

## 7. Сгенерированный код

*Состояние на 4.5:* генерируется один файл `tbr.gen.ts` с тремя таблицами процедур:
`clientProcedures` (кодировщики входов, декодеры выходов), `serverProcedures` (наоборот) и
`procedures` (всё, для тестов и `tbr decode`). Вместо двух файлов, описанных ниже, стороны
разделяет tree-shaking: каждый кодировщик и декодер — отдельная константа с `/* @__PURE__ */`,
и бандлер выкидывает то, что не попало в импортированную таблицу. Разбор и проверка каталога
колонок живут в runtime (`catalog`, `Check.cols`), в сгенерированном коде остаются только тела
колонок. Размеры и бюджет — [size.md](../bench/results/size.md), `node bench/size.mjs --budget`
в CI. Views и `toPlain` устроены так, как описано; `decode` на сервере — это `toPlain` поверх
верифицированного view.

**Клиент** (`generated/client.ts`): кодировщики входов, views выходов, верификаторы выходов
(подключаются в dev), таблица процедур.

```ts
class UserView implements User {          // implements ловит устаревший кодоген (§9)
  #b: Buf; #o: number;
  #name: string | undefined = undefined;  // кэш-слоты создаются в конструкторе: одна hidden class
  get id(): u32 { return this.#b.u32(this.#o, F_ID) as u32; }
  get name(): string { return this.#name ??= this.#b.str(this.#o, F_NAME); }
  toJSON() { return toPlainUser(this); }
}
```

- Views неизменяемы: присваивание полю бросает `TypeError`.
- Поля typed array у одиночного view — не геттеры, а неперечисляемые read-only свойства, созданные
  в конструкторе (`Object.defineProperty`). Геттер в горячем цикле (`for (...) s.t[i]`) движки не
  выносят из цикла: в Firefox и WebKit это было в 13–25 раз медленнее свойства. Создание view с
  четырьмя такими полями дороже на 0.1–0.3 µs.
- Вложенные views и строки мемоизируются, поэтому `user.pos === user.pos`.
- Вектор tables декодируется в настоящий `Array` из views (сами поля ленивые). Поэтому `map`,
  `filter`, spread массива, `Array.isArray` работают.
- `toPlain(value)` из `ts-bin-rpc/client` даёт глубокую копию из обычных объектов для spread
  объекта, `structuredClone`, RSC и мутаций. Spread самого view (`{...user}`) даёт объект без полей,
  это задокументированное ограничение. Состояние одиночного view лежит в `#private`, строки
  массива объектов держат колонки и номер строки под символьными ключами: `Object.keys`,
  `for...in`, JSON и `structuredClone` их не видят.
- Опция клиента `decode: 'eager'` отдаёт обычные объекты вместо views: на весь клиент, картой по
  путям процедур (`{ 'user.get': 'eager' }`, ключи проверяются по роутеру) или в `CallOptions` на
  один вызов. Вызов важнее записи процедуры, запись важнее общего режима, по умолчанию `'lazy'`.
  Это тот же `toPlain`, только внутри клиента: выход для мест, где views мешают.

**Сервер** (`generated/server.ts`): верификаторы и eager-декодеры входов, кодировщики выходов,
таблица процедур. На сервере вход декодируется в обычные объекты после верификации: входы обычно
маленькие, а хендлеры и будущие мидлвары получают обычные данные, которые можно менять.

**Кодировщик:** растущий буфер, запись вперёд. Строка классифицируется регуляркой как ASCII или
UTF-16 и попадает в свой блок. ASCII-блок пишется одним `TextEncoder.encodeInto`, а от 4 KB —
через `encode()` + `set`: в JavaScriptCore `encodeInto` на больших строках вдвое медленнее
([отчёт](../reports/Оптимизации%20строк%20и%20верификации.md)). Генерируется специализированная функция на каждый тип: урок protobuf-es —
специализация важнее формата.

## 8. Верификация

Сервер верифицирует каждый вход. Клиент по умолчанию верифицирует ответы в разработке и не
верифицирует в продакшен-сборке (`process.env.NODE_ENV === 'production'`, бандлер подставляет
значение при сборке; без бандлера проверка включена). Ответы приходят от своего сервера, и в
продакшене проверка — лишняя цена на каждый ответ, а в разработке она ловит рассинхрон схемы и
баги кодека. `verify: true` или `false` в `createClient` задаёт поведение явно, например
`verify: true` для чужого или недоверенного сервера.

Проверки:
- смещения и длины в пределах буфера;
- корректность vtable;
- блоки строк: в ASCII-блоке нет байтов с установленным старшим битом (проверка 32-битными
  словами, в 4–7 раз быстрее цикла по байтам), UTF-16-блок декодируется `TextDecoder` с
  `fatal: true` один раз и переиспользуется при чтении;
- индексы enum и теги union;
- лимит глубины (по умолчанию 64);
- **лимит суммарного числа элементов** против раздувания через повторное использование смещений.

Кодировщик проверяет типы и диапазоны: `-1`, `1.5` или `5n` в `u32` — `EncodeError`. Сообщение
называет путь до значения: `at [17].manager.age: expected u8, got 300`. На горячем пути путь не
отслеживается: после ошибки обёртка `encode` один раз проходит значение по описанию схемы, которое
лежит в сгенерированном файле данными. Ошибка выхода на сервере — это баг сервера, а не клиента:
клиент получает `500 BAD_OUTPUT` без деталей, `onError` — `EncodeError` с путём.

### Правила валидации

`Min`, `Max`, `MinLength`, `MaxLength`, `Pattern` — опциональные свойства с ключом-символом, как
бренды: `string & MaxLength<64>` принимает любую строку без каста. `source.ts` снимает их с
пересечения, `build.ts` проверяет место (числа, строки, массивы) и литеральность аргумента и кладёт
в IR поле `rules`. В `signature()` и lockfile правил нет, формат на проводе тот же: правило — не
часть контракта, его можно добавить или убрать без breaking-изменения.

`emit.ts` вшивает проверки в те же верификаторы под `c.rules &&`: слот таблицы, тело колонки,
вектор. Проверки — функции модуля (`ruleNum`, `ruleStrs`…), а не методы `Check`: бандл без правил,
то есть любой клиент, их выбрасывает, и генерированный код импортирует только нужные. Методами они
стоили клиентскому рантайму +0.7 KB gz, функциями — +0.07 KB. Чтение числа — геттером его типа прямо в сгенерированном цикле: общий `nums(kind)` со
`switch` по типу делал сравнение мегаморфным. Длина строки — из слота, без декодирования; `Pattern`
берёт подстроку из декодированного блока. Обратная ссылка в колонке строк указывает на уже
проверенную строку и пропускается. Регулярки — константы модуля, компилируются один раз.

Проверяет только сервер, только вход: клиент и стрим-клиент передают `rules: false`, выходы не
проверяет никто. `RuleError extends VerifyError` несёт `field`, `rule`, `limit`, `index`; сервер
отдаёт их в `data` у `400 BAD_INPUT`. Первая ошибка останавливает проверку: собрать все — значит
пройти сообщение целиком ещё раз. В `index` вложенного списка — сквозной номер во внутренней
колонке, а не пара индексов.

Типы не видят забытый `tbr generate`: бренд взаимно присваивается с базовым типом, `Same` в
`Contract` пропускает. Поэтому `tbr check` сравнивает существующий сгенерированный файл с тем, что
записал бы `generate`. Замер на 1000 объектов (Node 22, M3): 6 правил длины и диапазона на объект —
+23 мкс к верифицированному view за 10 мкс, ~4 нс на проверку; `Pattern` ещё на одной строке —
+30 мкс. По дороге: `u64`/`i64` сравниваются двумя 32-битными словами, а не `getBigInt64` —
BigInt на значение был самой дорогой проверкой; правила длины строк без `Pattern` читают только
ссылки колонки.

Ошибка верификации даёт ответ `400 BAD_INPUT` и не роняет процесс и соединение. Рантайм не
использует `eval` и `new Function`: код генерируется на этапе сборки, поэтому строгий CSP и Workers
работают.

## 9. Lockfile, эволюция и устаревший кодоген

`tbr.lock.json` коммитится, генерирует его `tbr generate`. Одна строка — одно поле, значение или
вариант, чтобы дифф lockfile читался как дифф контракта:

```json
{
  "format": 0,
  "procedures": {
    "user.get": { "input": "object user.get:input", "output": "object User" }
  },
  "objects": {
    "User": {
      "fields": {
        "id": { "id": 0, "type": "u32" },
        "email": { "id": 2, "type": "string" },
        "nick": { "id": 5, "type": "string | undefined", "retired": true }
      }
    }
  },
  "enums": { "Role": { "values": ["admin", "user", "guest"] } },
  "unions": {
    "Shape": {
      "discriminant": "kind",
      "variants": [{ "tag": "circle", "object": "Shape#circle" }, { "tag": "square", "object": "Shape#square" }]
    }
  }
}
```

Имена анонимных типов — путь до них: `user.get:input`, `User.meta`, `Shape#circle`. Два разных типа
с одним именем — ошибка: имя — ключ в lockfile.

Правила (из исследования форматов):
1. Lockfile только дописывается. ID удалённых полей помечаются `retired` и не переиспользуются.
   Вернуть поле с тем же именем можно только с тем же типом (получит старый ID); с другим типом —
   ошибка, которую не снимает `--allow-breaking`.
2. Переименование — только явно: JSDoc `@renamedFrom oldName` на поле. Без него переименование
   выглядит как удаление плюс добавление, и `check` подсказывает, какой `@renamedFrom` добавить.
3. Смена типа поля — несовместимое изменение. Исключение — опциональность: `T` → `T | undefined`
   безопасно, если тип не уходит в output; обратное — если тип не приходит во input.
4. Значения enum и варианты union только дописываются, их индексы фиксированы. Новое значение
   ломает старых клиентов, если тип есть в output; удалённое — если во input.
5. Новое обязательное поле ломает старых клиентов, если тип есть во input: они его не пришлют.
   Удалённое обязательное поле ломает их, если тип есть в output.
6. `tbr check` пересобирает lockfile в памяти и падает, если он отличается от закоммиченного; в
   выводе каждое изменение помечено `safe`, `breaking` или `error`. Это шаг в CI. `tbr generate`
   не пишет breaking-изменения без `--allow-breaking`.
7. `tbr generate --watch` сравнивает схему с lockfile таким, каким он был на старте watch (или после
   внешнего изменения, например checkout), а не с последним записанным. Иначе каждое сохранение
   попадало бы в lockfile: поле, добавленное и переименованное между двумя сохранениями, оставляло
   бы retired-запись со своим типом, а удаление обязательного поля из выхода блокировалось бы как
   breaking, хотя его ещё никто не видел.

**Устаревший кодоген ловится тремя слоями:**
1. `tbr generate --watch` перегенерирует за 10–20 ms на сохранение.
2. **На уровне типов:** сгенерированный файл импортирует роутер через `import type` и экспортирует
   тип `Contract`: для каждой процедуры сгенерированные типы входа и выхода должны быть взаимно
   присваиваемы с `InputOf<Router, 'user.get'>` и `OutputOf<…>`, набор процедур — совпадать.
   Интерфейсы в сгенерированном коде используют бренды (`u32`), поэтому ловится и смена `u32` на
   `u16`. Изменил тип и не перегенерировал — ошибка TS вида
   `Type 'StaleCodegen_RunTbrGenerate<"user.get output">' does not satisfy the constraint 'true'`.
3. **В рантайме:** сервер при старте сверяет роутер с таблицей процедур. Клиент шлёт хеш контракта
   процедуры (lockfile-записи всех достижимых из неё типов) в заголовке `x-tbr-schema`. При
   расхождении сервер по умолчанию пишет предупреждение (раз на процедуру) и обслуживает вызов:
   безопасные изменения совместимы, а старые клиенты во время выкатки — норма. `schemaMismatch:
   'error'` даёт `409 SCHEMA_MISMATCH`. Клиент с `debug: true` предупреждает о том же со своей
   стороны.

## 10. Протокол (HTTP, alpha)

- `POST {prefix}/{procedure}`, например `/rpc/user.get`. Тело запроса пустое, если у процедуры нет
  входа или вход опционален и не передан. Процедура без входа, но с контекстом —
  `(_: void, ctx: Ctx)`. Имя процедуры остаётся в пути: это читаемо
  в Network tab, логах и роутинге CDN, а длина URL при HPACK ничего не стоит. Хеш-ID эндпоинтов из
  первоначального плана отброшен.
- Тело — сообщение (§6). `Content-Type: application/vnd.tbr` (имя рабочее). Сервер отвечает `415`
  на любой другой тип: HTML-форма или simple request с чужого сайта процедуру не вызовет, для
  нашего типа браузер требует CORS preflight.
- Ответ `200` — сообщение выхода. Ошибки — конверт ошибки с полями `code`, `message`, `data?` и
  HTTP-статусом:

  | Код | Статус |
  |---|---|
  | `BAD_INPUT` | 400 |
  | `UNAUTHORIZED` | 401 |
  | `FORBIDDEN` | 403 |
  | `NOT_FOUND` | 404 |
  | `METHOD_NOT_ALLOWED` | 405 |
  | `CONFLICT`, `SCHEMA_MISMATCH` | 409 |
  | `PAYLOAD_TOO_LARGE` | 413 |
  | `UNSUPPORTED_MEDIA_TYPE` | 415 |
  | `TOO_MANY_REQUESTS` | 429 |
  | `INTERNAL` | 500 |
  | `BAD_OUTPUT` (процедура вернула значение не своего типа, например `300` в `u8`: TS это пропускает) | 500 |
  | `BAD_RESPONSE` (только на клиенте: ответ не сообщение или не прошёл верификацию) | 502 |

  Остальные коды — ошибки приложения, статус 400.

- Пользовательские ошибки: `throw new RpcError('FORBIDDEN', 'msg', data)` в хендлере, `data`
  уходит JSON-ом. На клиенте они превращаются в `RpcError` с тем же `code`, `status` и `data`.
  Остальные исключения клиент видит как `500 INTERNAL` без деталей, сервер передаёт их в
  `onError`.
- Сжатие отдаётся HTTP-слою: `Content-Encoding` ставит сервер или CDN, браузер распаковывает сам.
- Пост-alpha: GET для идемпотентных запросов (кэш), батчинг запросов, стриминг (§14).

## 11. Сжатие

Проблема из первого бенча (на строковых данных бинарь после brotli-11 на 47% больше JSON) решена в
фазе 0 ([compression.md](../bench/results/compression.md)). Сжатие портили смещения на каждую строку
данных и стартовые смещения строк: монотонно растущие числа для компрессора — шум. Колоночные
векторы, у строк — длины вместо смещений, дедупликация повторов внутри колонки:

| Данные | gzip-6 | brotli-4 | brotli-6 | brotli-11 | zstd-3 |
|---|---|---|---|---|---|
| 1000 юзеров | −8% | −17% | −20% | −10% | −7% |
| 500 товаров с длинным текстом | +5% | −5% | −4% | +1% | +2% |
| 20 юзеров (маленький ответ) | +5% | +8% | +4% | +8% | +6% |

Цель «паритет на brotli-4/6» достигнута, поэтому JSON-режим процедуры остаётся в бэклоге после alpha,
а не страховкой alpha.

## 14. Стриминг

Ниша — потоки мелких сообщений: телеметрия, графики, котировки. Здесь JSON-стримы (SSE, NDJSON)
платят парсингом за каждое сообщение, а колонки и typed arrays — главное преимущество формата.
Генераторы в основном API не используются: живые источники почти всегда отдают коллбэки, и
генератор над ними — лишняя обёртка. Реализовано в фазе 5; руководство —
[guide/streams.md](guide/streams.md), кадры — [FORMAT §12](FORMAT.md#12-кадры-потока).

### Сервер

```ts
import { stream, channel } from 'ts-bin-rpc/server';

export const appRouter = {
  // Свой источник: setup получает emit и { end, signal } и возвращает cleanup.
  ticks: async (input: { symbol: string }, ctx: Ctx) => {
    await requireUser(ctx); // ошибка до return — обычный HTTP-ответ с ошибкой
    return stream<Tick>((emit) => feed.on(input.symbol, (t) => emit(toTick(t))), { window: 16 });
  },
  // Раздача многим: батч топика кодируется один раз, байты уходят всем подписчикам.
  prices: (input: { symbol: string }) => prices.subscribe(input.symbol),
};
const prices = channel<Tick>();
feed.on('tick', (t) => prices.publish(t.symbol, toTick(t)));
```

- Процедура потоковая, если возвращает `Stream<T>` (или `Promise<Stream<T>>`). `Stream<T>` —
  интерфейс с фантомным полем под `unique symbol`; `tbr` узнаёт его по имени этого поля, а
  `AsyncIterable<T>`, `AsyncGenerator<T>` и `ReadableStream<T>` — по имени типа. Кодек выхода —
  батч `T[]`, сигнатура в lockfile — `stream <T>`, так что смена вызова на поток и обратно —
  breaking. Контракт в сгенерированном коде проверяет тип строки через `StreamItemOf`.
- Cleanup вызывается ровно один раз: клиент отписался, соединение оборвалось, сервер закрыл
  поток, строка не прошла кодирование, setup бросил исключение. `signal` из второго аргумента
  setup срабатывает тогда же.
- `emit` не отправляет сразу, а копит строки в батч. Батч уходит одним кадром, когда прошло
  `window` мс с первой строки (по умолчанию 16) или набралось `maxRows` строк (по умолчанию 512).
  `window: 0` отправляет в микрозадаче: склеиваются только синхронные `emit` одной задачи.
- Медленный клиент: очередь кадров на подписчика ограничена (`maxBuffered`, по умолчанию 4 МБ).
  Политика `overflow`: `'error'` (по умолчанию: поток закрывается ошибкой `SLOW_CONSUMER`) или
  `'drop-oldest'` (телеметрия, где важна свежесть). Async iterable читается только с той
  скоростью, с какой читает клиент.
- `end()` закрывает поток, `end(error)` — с ошибкой. Ошибка после первого кадра приходит кадром
  ошибки (тот же конверт, что в §10), а не HTTP-статусом. Не-`RpcError` уходит в `onError` и
  к клиенту приходит как `INTERNAL` без текста; строка, нарушившая свой тип, — `BAD_OUTPUT`.
- Устройство: на подписчика один `Sink` — очередь кадров и `ReadableStream` с `highWaterMark: 0`,
  который отдаёт всё накопленное одним чанком на каждый `pull`. Тело ответа читает рантайм (Bun,
  Deno, воркеры). `toNodeListener` берёт `Sink` ответа и пишет кадры в `res` сразу при `push`,
  без `ReadableStream`; когда `res.write` просит ждать `drain`, кадры копятся в той же очереди с
  тем же лимитом. Если мидлвар обернул тело ответа в новый `Response` или начал его читать,
  адаптер читает тело как есть. Heartbeat — пустой
  кадр, если 15 с ничего не уходило. `channel()` группирует подписчиков топика по кодировщику и
  кодирует батч один раз на группу.

### Клиент

```ts
const sub = api.ticks.subscribe({ symbol: 'BTC' }, (tick) => draw(tick.price));
sub.stop(); // для useEffect: return () => sub.stop()

api.ticks.subscribe({ symbol: 'BTC' }, {
  batch: (b) => chart.append(b.columns.t, b.columns.price), // Float64Array, Float32Array над кадром
  error: (e) => toast(e.message),
  end: () => {},
});

for await (const tick of api.ticks.subscribe({ symbol: 'BTC' })) {} // Subscription — AsyncIterable
```

- Подписка — только `api.x.subscribe(...)`; вызов `api.x(...)` у потоковой процедуры — `TypeError`.
  Процедура с именем `subscribe` побеждает.
- Коллбэк строки получает view строки батча, коллбэк батча — батч целиком: read-only массив строк
  и `columns`, где обязательные числовые, булевы и `Date` поля — typed arrays над байтами кадра
  (`columns()` у сгенерированного вектора; `columnsOf(rows)` из `ts-bin-rpc` для своих нужд).
  `columnsOf` находит колонки через сами строки и отдаёт их, только пока в массиве все строки
  view по порядку: у отфильтрованной, отсортированной или обрезанной копии — `undefined`.
  Массив не регистрируется в `WeakMap`: в SpiderMonkey ключ `WeakMap` переживает каждую малую
  сборку мусора вместе со всем view, и чтение 10 юзеров в Firefox было в 1.7 раза медленнее.
  Тип `Columns<T>` выводит конкретный массив из бренда: `f32` → `Float32Array`, `u32` →
  `Uint32Array`, `number` и `Date` → `Float64Array`, `boolean` → `Uint8Array`.
- Ошибки: ошибка сервера, `SLOW_CONSUMER`, `DISCONNECTED` (статус 0: тело кончилось без кадра
  конца или упала сеть), `BAD_RESPONSE` (битый кадр или не тот `Content-Type`). Без коллбэка
  `error` и без итераторов ошибка идёт в `console.error`. `end` не вызывается после `stop()`.
  Исключение в коллбэке пользователя не рвёт поток: оно перебрасывается в микрозадаче.
- С коллбэком запрос уходит сразу, без него — на первом `next()` итератора; `break` в
  `for await` останавливает подписку.
- `CallOptions.signal` останавливает подписку так же, как `stop()`. `decode: 'eager'` даёт plain
  objects, как у обычных процедур; `columns` есть в обоих режимах.
- Верификация кадров — по правилам §8: в разработке включена, в продакшене выключена.
- Клиент потоков (1.4 КБ gzip) не импортируется из `createClient`: сгенерированный код кладёт
  `subscribe` в `clientProcedures` только у потоковых процедур. Клиенты роутеров без потоков его
  не везут, рантайм остаётся 4.2 КБ.

### Провод

- Тот же `POST {prefix}/{procedure}`. Ответ — поток кадров с `Content-Type: application/vnd.tbr-stream`,
  `cache-control: no-store, no-transform` и `x-accel-buffering: no`.
- Кадр: заголовок 8 байт (`u32` длина полезной нагрузки, `u8` вид кадра, 3 байта резерва),
  полезная нагрузка дополнена до кратной 8, чтобы view строился без копирования. Виды: данные
  (сообщение `T[]`), ошибка, конец, heartbeat. Snapshot и delta зарезервированы под живое
  состояние ([FORMAT §12](FORMAT.md#12-кадры-потока)).
- Транспорты по очереди. Сейчас HTTP-стрим: тело ответа — `ReadableStream`, работает на
  `createHandler` в Node, Bun, Deno и Workers, backpressure даёт чтение клиента. Затем WebSocket:
  много подписок на одном соединении с ID подписки в заголовке кадра, обходит лимит в 6
  соединений на origin у HTTP/1.1. WebTransport — после: его датаграммы ложатся на
  `overflow: 'drop-oldest'`, но серверная поддержка в рантаймах и инфраструктура HTTP/3
  (сертификаты, балансировщики) пока слабые, проверить перед реализацией. Клиентский API от
  транспорта не зависит.

### Замеры

До кода: поток из 1024 тиков (`t`, `price: f32`, `size: u32`, `side`), кодирование на сервере,
кадры с префиксом длины, чтение каждого поля на клиенте. Скорость относительно NDJSON
([stream.md](../bench/results/stream.md)):

| Вариант | Node | Chromium | Firefox | WebKit |
|---|---|---|---|---|
| JSON, батчи по 32 | 1.9× | 3.2× | 1.8× | 2.2× |
| бинарь, кадр на тик | 1.7× | 0.91× | 0.63× | 0.96× |
| бинарь, батчи по 8 | 6.6× | 5.9× | 2.4× | 4.0× |
| бинарь, батчи по 32 | 16× | 15× | 6.0× | 8.8× |
| бинарь, батчи по 128 | 23× | 25× | 10× | 15× |

Кадр на каждый тик не быстрее NDJSON в браузерах: дорого кодирование маленького сообщения
(`Writer` на каждое). Отсюда батчинг по умолчанию.

После кода, на настоящем транспорте: Node-сервер на 127.0.0.1, страница в Chromium читает каждое
поле, у NDJSON и SSE тот же продюсер и одна запись на задачу
([stream-transport.md](../bench/results/stream-transport.md)):

| Нагрузка | Вариант | Задержка p50 | Main thread страницы | Байты |
|---|---|---|---|---|
| 1 000 тиков/с, 5 с | окно 16 мс | 9.1 мс | 62 мс | 105 КБ |
| | окно 0 | 0.30 мс | 312 мс | 333 КБ |
| | NDJSON | 0.23 мс | 287 мс | 335 КБ |
| | SSE | 0.20 мс | 187 мс | 368 КБ |
| 20 000 тиков/с, 3 с | окно 16 мс | 9.6 мс | 147 мс | 1.0 МБ |
| | окно 0 | 0.35 мс | 261 мс | 1.2 МБ |
| | NDJSON | 0.30 мс | 279 мс | 3.7 МБ |
| | SSE | 0.26 мс | 429 мс | 4.1 МБ |

Окно 16 мс стоит ~10 мс задержки и в 1.9–4.6 раза дешевле NDJSON по main thread. С окном 0
задержка как у NDJSON, main thread тоже (0.9–1.1×): на редких тиках каждый кадр — отдельный чанк
`ReadableStream` и отдельный view. CPU сервера с окном 0 выше, чем у NDJSON, на 15–45%. 200 000 тиков на
полной скорости: 46 мс против 85 мс у NDJSON и 750 мс у SSE.

### Открытые вопросы

- Переподключение: автоматически с backoff или руками. Для событий без живого состояния
  пропущенные кадры не восстанавливаются.
- Сжатие потока: `Content-Encoding` у HTTP-стрима сжимает с общим контекстом, а с ним кадры в
  1.9–2.5 раза меньше ([realtime-size.md](../bench/results/realtime-size.md)). Но буфер
  компрессора добавляет задержку.
- ~~Стоимость кадра с `window: 0`~~: в Node кадры идут в `res.write` мимо `ReadableStream`.
  CPU сервера на кадр 12.1 → 11.2 мкс (клиент — curl в своём процессе, кадр на каждый
  `setImmediate`), в бенче выше 855 → 811 мс на 1 000 тиков/с и 539 → 504 мс на 20 000.
  Остальное — `setImmediate`, кодирование кадра и системный вызов на каждый `res.write`.
- enum в `columns` как индексы: сейчас не отдаются.
- Живое состояние (snapshot + delta, кольцевые буферы): отдельный дизайн поверх кадров.

## 15. Мидлвары

Роутер остаётся объектом обычных функций, без билдеров процедур в духе
`t.procedure.use().input().query()`. Мидлвары оборачивают поддерево роутера функцией `use()`;
руководство — [guide/middleware.md](guide/middleware.md).

```ts
const authed = middleware(({ ctx }: Call<Ctx>): Authed => {
  if (!ctx.user) throw new RpcError('UNAUTHORIZED', 'sign in first');
  return { ...ctx, user: ctx.user };
});
const timed = around(async ({ path }, next) => { /* … */ return next(); });

export const appRouter = use([timed], {
  account: use([authed], {
    me: async (_, ctx) => ctx.user,                                   // ctx: Authed, входа нет
    rename: async (input: { name: string }, ctx) => ctx.db.rename(ctx.user.id, input.name),
  }),
});
```

- Два вида шагов. `middleware(fn)` выводит контекст: возвращает `ctx` следующего шага, бросает —
  ошибка вызова. `around(fn)` оборачивает остаток цепочки: `next()` запускает его и возвращает
  результат процедуры, `next(ctx)` передаёт другой контекст (транзакция), без `next()` шаг отвечает
  сам (кэш). Оба получают один объект `call = { path, input, ctx }` на запрос.
- Порядок: декодирование и проверка входа → шаги цепочки снаружи внутрь → процедура → кодирование
  выхода. Мидлвара не видит битых байтов. Ошибки шагов обрабатываются как ошибки процедуры:
  `RpcError` уходит клиенту, остальное — в `onError` и `INTERNAL`.
- Типы. `use()` возвращает роутер, где у каждой процедуры `ctx` заменён на контекст, нужный
  цепочке снаружи (`ChainNeeds`): шаг контекста требует свой `In` и отдаёт `Out`, `around` без
  типов пропускает контекст как есть (`Keep`). Процедура без `ctx` за цепочкой, которой контекст не
  нужен, остаётся без второго параметра, так что `RouterContext` у остального роутера не
  размывается в `unknown`.
- Контекстная типизация. Ограничение дженерика `R` у `use()` — `RouterIn<M>`: процедуры вида
  `(input: never, ctx: ChainGives<M>) => unknown`, где `ChainGives` — контекст, который цепочка
  отдаёт процедурам. TS типизирует из ограничения параметры без аннотаций: `ctx` получает контекст
  цепочки, неиспользуемый вход — `never`, и `tbr` читает `never` как «входа нет», так же как `void`.
  Аннотированный вход совместим с `never`, аннотировать нужно только его. Вход без аннотации,
  который процедура читает, — ошибка типов, а не молчаливый `any`. Так `ctx: Authed` и `_: void`
  пишутся только вне `use()`, где контекст брать неоткуда.
- Проверка контекста. Если в цепочке есть шаг, выводящий контекст, ограничение строгое: с
  `strictFunctionTypes` параметр `ctx` проверяется контравариантно, и процедура, которой нужно
  больше, чем даёт цепочка, получает ошибку на себе: `Property 'db' is missing in type 'Authed'`.
  Цепочка из одних `Keep` знает только нижнюю границу, процедуре может быть нужно больше снаружи:
  там ограничение через метод, параметры бивариантны. Несовместимые шаги между собой ловит
  rest-параметр `contextMismatch: ContextMismatch<needs, got>` (`Expected 3 arguments`); он
  зависит только от цепочки, не от `R`, иначе вывод `R` зацикливается.
- Результат `use()` — `NoInfer<WithContext<…>>`. Вложенный `use()` получает контекстный тип от
  внешней цепочки, и TS выводил бы его `R` обратно через `WithContext`, а это цикл (TS 7) или
  «Excessive stack depth» (TS 5.9 и 6). Условный тип вместо `NoInfer` чинит TS 7, но не 5.9 и 6.
  `tbr` разворачивает `NoInfer` (тип-подстановку) при обходе роутера.
- `tbr` читает сигнатуры через mapped-тип `WithContext` как обычные: параметры —
  `(input: I, ctx: C)`, а не rest-кортеж, иначе `getParameters()` вернул бы один параметр.
  Опциональный вход с контекстом становится `(input: I | undefined, ctx: C)`.
- Цена. `use()` собирает функцию на процедуру сразу, вложенные `use()` сливаются в одну цепочку.
  `createHandler` разворачивает обёртку и собирает цепочку заново с полным путём, один раз при
  старте. На запрос — только шаги процедуры и один объект `call`; синхронный шаг контекста не ждёт
  микрозадачу. Замер ([middleware.md](../bench/results/middleware.md)): шаг контекста +20 нс,
  асинхронный +75 нс, `around` +120 нс; вызов через `createHandler` без входа и выхода — ~4 мкс.
- `context(request)` вызывается только для процедур с `ctx`: `tbr` ставит `ctx: true | false` в
  серверную таблицу, в `Contract` проверяется `TakesContext`, так что добавленный без
  `tbr generate` параметр ловит `tsc`. Нет поля (код до 0.1.0-alpha.3) — контекст строится всегда.
  Процедура за цепочкой, которой контекст не нужен, `ctx` не принимает и его не получает. Дорогое
  (сессия, пользователь) — в шаге `middleware()`, `context` — только дешёвое: запрос, `db`.
- Стримы: цепочка заканчивается, когда процедура вернула поток; `around` охватывает установку
  потока, не его жизнь.
- Бизнес-валидация (длины, форматы, диапазоны) — не мидлвара: это теги в типах
  (`string & MaxLength<64>`, §8), которые `tbr` вшивает в верификатор входа, без второго прохода
  по объекту. Кросс-полевые правила — планируемый хук `refine` по имени типа, он же примет Standard
  Schema (Valibot, Zod) для тех, у кого схемы уже есть.

## 16. Запросы и HTTP-кэш

По умолчанию вызов — `POST`, и HTTP-кэши его не хранят. `query()` помечает процедуру без
побочных эффектов: клиент шлёт её `GET`-ом, браузер, CDN и `304 Not Modified` работают.
Руководство — [guide/queries.md](guide/queries.md).

```ts
export const appRouter = {
  products: query(async (input: { category: string }) => db.products(input), { maxAge: 60 }),
  catalog: query({ brands: async () => db.brands() }, { public: true, maxAge: 300 }),
  account: use([authed], { profile: query(async (_, ctx) => ctx.db.profile(ctx.user.id)) }),
};
```

- Обёртка, а не JSDoc-тег: опечатку в опциях ловят типы, стиль — как у `use()` и `stream()`.
  `query(target, options?)`: процедура или неймспейс, опции вторым аргументом. Процедуры остаются
  теми же функциями.
- Как узнаёт клиент. `query()` возвращает тип с фантомным брендом `[tbrQuery]: true`, `tbr` видит
  его через компилятор, как `Stream<T>`, и пишет `get: true` в обе таблицы. `WithContext` бренд
  сохраняет, так что `use()` снаружи и внутри `query()` — оба порядка работают. В `Contract`
  проверка `IsQuery`: добавленный без `tbr generate` `query()` ловит `tsc`. Опции (`maxAge`,
  `public`) в типы и кодоген не попадают: сервер читает их из `WeakMap` по функции при старте.
- Типы `query()`: перегрузка неймспейса с `R extends AnyRouter`, перегрузка процедуры с `F` без
  ограничения. С `F extends AnyProcedure` параметры `query(async (_, ctx) => …)` внутри `use()`
  получали `any` из ограничения раньше, чем доходил контекст цепочки.
- Провод: `GET {prefix}/{path}?h=<хеш контракта>&i=<вход base64url>`. Вход — те же байты, что тело
  POST, сервер идёт тем же путём: верификация, мидлвары, процедура. Хеш в URL, а не в заголовке:
  кэши ключуют по URL, после выкатки нового контракта старый кэш не попадает. Своих заголовков у
  GET нет — cross-origin запрос остаётся простым, без preflight.
- Вход длиннее 2 KB base64url — клиент сам шлёт POST: прокси обычно режут URL за 8 KB. Сервер
  принимает у запроса оба метода; GET к обычной процедуре — 405 с `Allow: POST`.
- `Cache-Control`: `private` по умолчанию, `public` только явно, `max-age` из опций, без него
  `no-cache` (каждый раз ревалидация). Ошибки GET — `no-store`. Политика статическая: выставлять
  её из мидлвары или дефолт из конфига `createHandler` — на будущее.
- `ETag` — 64-битный хеш тела: две дорожки в духе murmur3 по 32-битным словам. Не
  криптографический: он различает версии одного URL. `crypto.subtle.digest` асинхронный и в Node
  стоит ~9 мкс на любой ответ; JS-хеш — 0.07 мкс на 150 байт и 40 мкс на 100 KB против 50 мкс у
  SHA-256. `If-None-Match` с совпадением (`*`, слабые теги, список) — `304` без тела. Процедура при
  этом выполняется: 304 экономит трафик и декодирование, не работу сервера.
- Цена в процессе, клиент и хендлер вместе ([query.md](../bench/results/query.md)): POST ~11 мкс,
  тот же вызов GET-ом ~9 мкс, ответ 304 ~4 мкс. У GET нет тела, чтение `request.arrayBuffer()`
  дороже base64url и хеша.
- CSRF: у POST защита — обязательный content type, у GET её нет, и любая страница может отправить
  его с куками пользователя. Безопасно, пока процедура без побочных эффектов — это и есть контракт
  `query()`. Ответ чужой странице без CORS всё равно не прочитать.
- Стрим не может быть запросом: ошибка `tbr` и проверка при старте `createHandler`.
- Не делает: кэш в памяти приложения, дедупликацию, инвалидацию — это TanStack Query.

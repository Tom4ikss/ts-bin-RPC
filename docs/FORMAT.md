# Формат сообщения v0

Статус: зафиксирован по итогам фазы 0 (2026-11-02). Версия формата в заголовке — `0`. До 1.0 формат
может меняться, но только с повышением версии.

Обоснования ссылаются на замеры в [`bench/results/`](../bench/results/): Node 22.13, Chromium 156,
Firefox 157, WebKit 27.2, Apple M3 Pro.

## 1. Общие правила

- Порядок байтов — little-endian.
- Сообщение — отдельный `ArrayBuffer`. Все смещения — `u32` от начала сообщения.
- Выравнивание задаётся там, где читатель создаёт `TypedArray` поверх буфера: колонки и векторы
  скаляров выровнены по размеру элемента, блок UTF-16 — по 2. Row tables читаются через `DataView`,
  их поля выравнивания не требуют, но кодировщик выравнивает их естественно.
- Лимиты по умолчанию (настраиваются): сообщение — 64 MB, глубина вложенности — 64, суммарное число
  элементов во всех векторах — 16 M.

## 2. Заголовок

| Смещение | Поле | Тип |
|---|---|---|
| 0 | magic `T` `B` (`0x54 0x42`) | 2 байта |
| 2 | версия формата (`0`) | u8 |
| 3 | флаги | u8 |
| 4 | смещение корневого значения | u32 |
| 8 | смещение блока ASCII | u32, только при `STRINGS` |
| 12 | длина блока ASCII (байты = символы) | u32, только при `STRINGS` |
| 16 | смещение блока UTF-16 | u32, только при `STRINGS` |
| 20 | длина блока UTF-16 (символы) | u32, только при `STRINGS` |

Флаги:

| Бит | Имя | Значение |
|---|---|---|
| 0 | `STRINGS` | в сообщении есть строки, в заголовке есть дескрипторы блоков (иначе заголовок 8 байт) |
| 1 | `ERROR` | корень — конверт ошибки (§9), а не выход процедуры |
| 2–7 | — | зарезервированы, должны быть 0 |

Читатель отвергает неизвестную версию и ненулевые зарезервированные биты.

## 3. Строки

Все строки сообщения лежат в двух блоках:

- **Блок ASCII** — строки, все code units которых меньше `0x80`. Индекс символа совпадает с индексом
  байта.
- **Блок UTF-16LE** — все остальные строки, по 2 байта на code unit.

Кодировщик кладёт строку в блок ASCII тогда и только тогда, когда она целиком ASCII. Строки с
одиночными суррогатами кодировщик отвергает: UTF-16-декодер браузера заменил бы их на U+FFFD.

Читатель декодирует каждый блок **одним вызовом** `TextDecoder` (ASCII — как `utf-8`, второй блок —
`utf-16le`) при первом обращении к любой строке этого блока. Значение поля — `substring` блока.
Строки мемоизируются.

*Почему так.* Каждый вызов `TextDecoder` в браузере стоит ~100 ns независимо от длины, а
`JSON.parse` создаёт короткую строку за 12–40 ns. Декодирование блока целиком плюс `substring`
быстрее `JSON.parse(bytes)`: на ASCII в 2–3 раза в Chromium, на кириллице в 1.5–3 раза
([strings.md](../bench/results/strings.md)). Кириллица в UTF-8 декодируется медленно везде, кроме
Firefox, поэтому всё не-ASCII идёт в UTF-16. По размеру кириллица в UTF-16 равна UTF-8.

**Ссылка на строку в row table** (8 байт): `u32 start` (индекс символа в блоке), затем
`u32 (len << 1) | block`, где `block` 0 — ASCII, 1 — UTF-16.

**Строковая колонка** (§6) хранит не начала, а длины: `u32 asciiBase`, `u32 u16Base`, затем `u32 ref`
на каждую строку данных:
- `(len << 2) | (block << 1)` — новое значение. Значения колонки идут в блоке подряд, начиная с
  `asciiBase` или `u16Base`, в порядке строк данных.
- `(row << 1) | 1` — то же значение, что у более ранней строки данных `row` этой колонки
  (дедупликация внутри колонки).

Начала читатель вычисляет одним проходом префиксной суммы при первом обращении к колонке. Длины и
обратные ссылки — маленькие повторяющиеся числа, и они сжимаются лучше монотонных смещений: только
из-за этого строковый CRUD стал меньше JSON после сжатия ([compression.md](../bench/results/compression.md),
вариант L против A/B).

## 4. Скаляры

| Тип IR | Байты | Примечание |
|---|---|---|
| bool | 1 | 0 или 1, иное — ошибка верификации |
| u8, i8 | 1 | |
| u16, i16 | 2 | |
| u32, i32, f32 | 4 | |
| f64 (`number`) | 8 | |
| u64, i64 | 8 | на клиенте `bigint` |
| timestamp (`Date`) | 8 | f64, миллисекунды с эпохи |
| enum | 1 или 2 | индекс значения из lockfile; u16, если значений больше 256 |

Кодировщик проверяет диапазоны: `-1` или `1.5` в `u32` — ошибка кодирования.

## 5. Row table (одиночный объект)

Используется для объекта, который не является элементом вектора: корень ответа, вложенное поле
row table.

```
T:      i32 vtBack            vtable лежит по адресу T - vtBack
T+4...  поля
vtable: u16 vtSize            размер vtable в байтах
        u16 tableSize         размер таблицы в байтах
        u16 fieldOff[k]       k = (vtSize - 4) / 2, индекс = ID поля из lockfile
```

- `fieldOff[id]` — смещение поля от `T`; `0` означает, что поля нет. Поля с `id >= k` отсутствуют.
  Так работает эволюция: старый читатель не видит новых полей, новый видит удалённые как
  отсутствующие.
- Одинаковые vtables кодировщик записывает один раз.
- Значения полей: скаляры — на месте, строка — 8-байтовая ссылка (§3), вложенный объект — `u32`
  смещение его row table, вектор — `u32` смещение вектора (§6), union — `u8` тег + `u32` смещение
  (§7).
- Отсутствие и `null`: для `x?: T` отсутствующее поле — `undefined`. Для `x: T | null` — `null`.
  Для `x?: T | null` перед значением стоит `u8` тег присутствия (0 = `null`, 1 = значение), а
  отсутствие поля означает `undefined`.

*Почему vtable.* Цена косвенности на чтении 1000 юзеров — 3–18% на полном чтении и до ~30% на
чисто числовых полях в Firefox и WebKit. При этом всё равно получается в 12–27 раз быстрее JSON
([layout.md](../bench/results/layout.md)). Эволюцию схемы vtable даёт бесплатно.

## 6. Векторы

| Объявленный тип | Раскладка | На клиенте |
|---|---|---|
| `T[]` скаляров | `u32 count`, выравнивание, элементы подряд | копия в `Array` |
| `Float32Array` и другие `TypedArray` | `u32 count`, выравнивание по элементу, элементы | `TypedArray` без копирования |
| `Uint8Array` | `u32 count`, байты | `subarray` без копирования |
| `string[]` | `u32 count`, затем строковая колонка (§3) | `Array` строк |
| `T[]` объектов | **колоночный вектор** | `Array` из views |

**Колоночный вектор** — элементы вектора объектов хранятся по колонкам, по одной на поле:

```
u32 count
u16 ncols, u16 reserved
ncols × { u16 fieldId, u16 colFlags, u32 colOffset }    каталог колонок
```

- Колонки, которых нет в каталоге, отсутствуют у всех элементов (эволюция, как у vtable).
- `colFlags`: бит 0 — `OPTIONAL`, перед данными колонки лежит битовая карта присутствия
  `(count + 7) >> 3` байт; бит 1 — `NULLABLE`, затем битовая карта `null`.
- Вид колонки определяется типом поля в схеме:
  - **скаляр** — элементы подряд, выравнивание по размеру;
  - **строка** — строковая колонка (§3);
  - **вложенный объект** — смещение вложенного колоночного вектора с тем же `count`;
  - **вектор** — `u32 offsets[count + 1]` в дочерний вектор суммарной длины (как list column в
    Arrow);
  - **union** — колонка тегов `u8`, колонка индексов `u32` и по колоночному вектору на вариант
    (dense union).
- Читатель создаёт `TypedArray` колонки лениво, при первом обращении к полю.

*Почему колонки.* Сжатый строковый CRUD становится на 7–20% меньше JSON на gzip, brotli-4/6/11 и
zstd-3. С построчными таблицами было на 48–61% больше
([compression.md](../bench/results/compression.md)). Скорость полного чтения та же, что у row tables
(в 2.4–3.1 раза быстрее JSON). Частичное чтение быстрее JSON в 4.2–8.2 раза, кодирование — самое
быстрое из вариантов ([layout.md](../bench/results/layout.md)). Числовые колонки отдаются как
`TypedArray`, это главный сценарий проекта.

## 7. Unions

Discriminated union одиночного значения: `u8` тег (индекс варианта из lockfile по значению
дискриминанта) и `u32` смещение row table варианта. Поле-дискриминант в таблицу варианта не пишется:
его значение восстанавливается из тега. В векторе — dense union (§6).

## 8. Верификация

Верификатор проходит сообщение по схеме до того, как отдать его пользователю. Сервер верифицирует
каждый вход, клиент — в dev-режиме или по опции. Проверки:

1. Заголовок: magic, версия, зарезервированные биты, корень и блоки в пределах сообщения, блок UTF-16
   выровнен.
2. Каждое смещение и длина — в пределах сообщения. Смещение выровнено там, где поверх него создаётся
   `TypedArray`.
3. vtable: `vtSize` чётный и не меньше 4; каждое `fieldOff` плюс размер поля не выходит за
   `tableSize`.
4. Строки: начало и длина в пределах блока, в блоке ASCII все байты меньше `0x80`. Обратная ссылка в
   колонке указывает на более раннюю строку данных, которая не является обратной ссылкой. Сумма длин
   колонки не выходит за блок.
5. bool — 0 или 1; enum и теги union — в пределах известных значений; `offsets` list column не
   убывают и не выходят за дочерний вектор.
6. Глубина вложенности и суммарное число элементов — в пределах лимитов. Это защищает от раздувания:
   повторно использованные смещения не позволят короткому сообщению развернуться в огромные массивы.

Ошибка верификации — `BAD_INPUT`, процесс и соединение живут дальше.

## 9. Конверт ошибки

Флаг `ERROR`, корень — row table с фиксированной схемой, не зависящей от процедуры:

| ID | Поле | Тип |
|---|---|---|
| 0 | `code` | string |
| 1 | `message` | string |
| 2 | `data` | bytes, UTF-8 JSON, опционально |

## 10. Маленькие сообщения (realtime)

Сообщение без строк имеет 8-байтовый заголовок. Кадр из 10 сущностей (`u32` + 4×`f32` + `u16`)
кодируется и декодируется в 5–11 раз быстрее JSON, из 100 сущностей — в 27–72 раза. С
permessage-deflate с контекстом кадр на 16–20% меньше JSON
([realtime.md](../bench/results/realtime.md), [realtime-size.md](../bench/results/realtime-size.md)).
Каталог колонок после сжатия ничего не стоит, поэтому он обязателен. Дельта-кодирование — пост-alpha.

## 11. Что осталось открытым

- Struct (замороженная раскладка без vtable) для маленьких числовых типов — пост-alpha.
- Дельты и снапшоты для стриминга — пост-alpha, отдельным форматом кадра поверх этого.
- `Map`, `Record`, кортежи — пост-alpha.
- Маленькие колоночные векторы (до ~10 элементов) пока медленнее row tables (в Chromium 1.3x
  против 2.1x к JSON) из-за создания колонок. Ленивое создание колонок должно это закрыть, проверка —
  в фазе 2.

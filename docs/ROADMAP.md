# Роадмап до alpha и публикации

Режим проекта: сначала пет, архитектура с запасом на рост ([DESIGN.md](DESIGN.md)). Сроков нет,
размер задач указан относительно: S — вечер, M — несколько вечеров, L — неделя и больше.
Каждая фаза заканчивается проверяемым критерием выхода.

## Фаза 0 — замеры и фиксация формата

Цель: не строить кодоген поверх формата, который потом придётся менять.

**Статус: выполнена 2026-11-02.** Результаты — [`bench/results/`](../bench/results/), формат —
[FORMAT.md](FORMAT.md). Что изменилось по сравнению с планом:
- Строки — два блока на сообщение (ASCII + UTF-16), декодирование одним вызовом. Именно это
  перевернуло полное чтение CRUD в браузерах с проигрыша (0.8–1.06x) на выигрыш (2.4–3.1x).
- Векторы объектов — колоночные: так сжатый CRUD стал меньше JSON. JSON-режим в alpha не нужен.
- Не сделано: прогон CI на GitHub не проверен; бенч против Colyseus перенесён на после alpha.

## Фаза 1 — кодоген: от типов до IR

**Статус: выполнена 2026-11-02.** Код — [`packages/cli`](../packages/cli), golden-снапшоты —
[`packages/cli/test/__snapshots__`](../packages/cli/test/__snapshots__). Что изменилось по сравнению
с планом:
- Батчинга запросов к TS-Go нет: фикстура на 20 типов собирается за ~140 мс вместе со стартом
  процесса. Вернёмся, когда будет медленно на настоящем проекте.
- `tbr rename` не сделан, переименование — только `@renamedFrom`.
- Классификация учитывает направление: тип, достижимый из input, ломает новое обязательное поле;
  тип, достижимый из output, — удалённое поле, новое значение enum и новый вариант union.
- `T | undefined` и `T | null` нельзя класть в элементы массива, `null`/`undefined` в результате
  процедуры тоже запрещены. Объединения числовых литералов отвергаются до появления числовых enum.
- Union-члены перегруппировываются по аннотации поля: иначе `role?: Role` терял имя алиаса.

## Фаза 2 — runtime кодека и эмиттеры

**Статус: выполнена 2026-11-02.** Runtime — [`packages/ts-bin-rpc/src/runtime.ts`](../packages/ts-bin-rpc/src/runtime.ts),
эмиттер — [`packages/cli/src/emit.ts`](../packages/cli/src/emit.ts), `tbr generate` пишет `tbr.gen.ts`
рядом с роутером. Бенч — [`bench/results/generated.md`](../bench/results/generated.md). Что изменилось
по сравнению с планом:
- Раскладка уточнена при реализации и описана в [FORMAT.md](FORMAT.md): корень — слот, union — 5 байт
  (смещение, потом тег), тег присутствия `x?: T | null` стоит после значения, поля-литералы не
  пишутся, пустые дочерние векторы — нулевое смещение (иначе рекурсивные типы кодировались бы
  бесконечно), вложенные объекты в колонках — плотный вектор плюс rank по битовым картам.
- Вместо `Buf` три класса: `Writer`, `Reader`, `Check`. Верификатор проверяет UTF-16-блок (UTF-8 в
  формате нет), считает глубину по контейнерам и ограничивает число узлов. `view` и `decode`
  верифицируют по умолчанию.
- Eager-декодер — это `toPlain(view)`, отдельного эмиттера декодеров нет. Даже так `decode` на
  полном чтении 1000 юзеров в 2.9–4 раза быстрее JSON в браузерах.
- Фаззинг: ~94% мутаций отвергаются, остальные читаются целиком без исключений.
- Скорость, сгенерированный код к ручному `codec3` (время, меньше — лучше): чтение в Chromium
  0.92–1.10, в WebKit 0.94–1.02; кодирование в Chromium, Node и Firefox быстрее ручного, в WebKit —
  1.10–1.16. Ручной кодек не проверяет ни типов, ни диапазонов, это и есть разница в JSC. Firefox
  и Node на этой машине шумят на ±20% между прогонами, там цифры в пределах шума.
- По дороге: аксессоры колонок создаются сразу при обращении к
  вектору (ленивые по полям замедляли полное чтение на ~40%), ASCII-проверка через regex, writer
  запоминает размер прошлого сообщения. В харнессе бенча сэмплы вариантов чередуются, у каждого
  варианта свой цикл чтения: общий собирал фидбек со всех вариантов, и результат зависел от порядка.

## Фаза 3 — сервер, клиент, протокол

**Статус: выполнена 2026-11-03.** Код — [`packages/ts-bin-rpc/src`](../packages/ts-bin-rpc/src)
(`server.ts`, `client.ts`, `node.ts`, `rpc.ts`, `router.ts`), приложение-фикстура и тесты —
[`e2e/`](../e2e). Что изменилось по сравнению с планом:
- Один сгенерированный файл `tbr.gen.ts` на обе стороны. Разделение сделано в 4.5 через tree-shaking.
- Хеш контракта — на процедуру: lockfile-записи всех типов, достижимых из неё. Расхождение по
  умолчанию только предупреждение, `schemaMismatch: 'error'` даёт 409: старые клиенты во время
  выкатки — норма, правила эволюции их защищают.
- Проверка на типах — тип `Contract` в сгенерированном файле: взаимная присваиваемость
  сгенерированных типов и типов роутера плюс точный набор процедур. Вместо `implements` исходных
  типов: так не нужно импортировать каждый тип пользователя по имени, а анонимные типы проверяются
  тоже. Сервер дополнительно сверяет роутер и таблицу процедур при старте.
- Сервер принимает только `application/vnd.tbr` (415 иначе) — защита от CSRF через формы и simple
  requests.
- Добавлены `ts-bin-rpc/node` (адаптер Fetch-хендлера для `node:http`), процедуры
  `(_: void, ctx)`, `CallOptions` (`signal`, `headers`) последним аргументом клиента.
- Ошибки кодирования называют путь до значения (`at [17].manager.age: expected u8, got 300`), выход
  не своего типа — `500 BAD_OUTPUT`. Тест со случайно испорченными значениями нашёл, что bigint в
  целочисленном поле ронял проверку сырым `TypeError`.
- Bun и Deno проверяются только в CI (`E2E_RUNTIMES=node,bun,deno`), локально их нет.

## Фаза 4 — DX и подготовка к alpha

**4.3 выполнена 2026-11-03.** Руководство в [`docs/guide`](guide) (на английском): introduction,
getting started, types, views, server and client, evolution, CLI, performance, FAQ. Сайт — `site/`
на Astro Starlight: лендинг с графиком бенчей, поиск Pagefind, светлая и тёмная темы. Страницы он
читает прямо из `docs/guide`. Каждое утверждение руководства сверено с кодом. Что нашлось:
- В views строк массива объектов `{...row}`, `Object.keys` и `structuredClone` видели служебные
  `$tbrCols`/`$tbrRow`. Исправлено: состояние строки теперь под символьными ключами, `Object.keys`
  даёт `[]`, `structuredClone` — `{}`, как у одиночного view. Замер на текущем харнессе (сэмплы
  чередуются, у варианта свой цикл), к строковым полям: символы 0.91–1.05 во всех движках,
  `#private` в Firefox 0.79–0.93, `Object.defineProperty` 0.07–0.77. Худший случай символов — числовое
  чтение в V8, 0.91–0.94. Прежние «10–30%» мерились старым харнессом с общим циклом чтения. Рецепт для spread — `toPlain`.
- `Date` в строках массива — новый объект на каждое чтение, в одиночных views мемоизирован.
- Опции `decode: 'eager'` на клиенте, которую обещал DESIGN §7, не было. Сделана 2026-11-03: на
  весь клиент, картой по процедурам и в `CallOptions`.
- Цифры «быстрее JSON» на сайте и в руководстве — с верификацией, она включена по умолчанию.

**4.1 выполнена 2026-11-03.** `tbr generate --watch` держит один проект TypeScript открытым и на
каждую пачку изменений делает новый snapshot. Компилятор переиспользует неизменённые файлы:
snapshot 7–15 ms, сборка схемы и запись 5–10 ms, вся перегенерация 10–20 ms на playground, e2e и
примере (цель была < 300 ms). Что выяснилось:
- `Snapshot.update({ fileNotifications })` в 7.1.0-beta возвращает новый snapshot и новый checker,
  но типы в нём старые, даже с `invalidateAll` и со слоем `fileSystem`. Свежий `createSnapshot` с
  теми же нотификациями видит изменения и почти так же быстр, его и используем.
- Lockfile в watch сравнивается с тем, что был на старте (DESIGN §9, п. 7). Иначе промежуточные
  сохранения сжигали бы ID и блокировались как breaking.
- macOS присылает события записей, сделанных перед стартом watch: одна лишняя перегенерация,
  безвредно.

В примере Vite запускает watch сам; в playground `pnpm watch`.

**4.2 выполнена 2026-11-03.** [`examples/dashboard`](../examples/dashboard): сервер на Node, клиент на
Vite и React, графики uPlot. В dev роутер работает внутри Vite (`ssrLoadModule`), правки роутера
применяются со следующего вызова. Колонки ответа уходят в uPlot как есть, без копирования.
Клиентский бандл — 9.1 KB gz без React и uPlot. Найдено по ходу:
- `toNodeListener` логировал как ошибку каждый запрос, который клиент отменил. В live-режиме с
  `AbortController` это происходит постоянно. Теперь он молчит, если запрос или ответ уже
  закрыты.
- Без tsconfig `tbr generate` писал «could not load TypeScript project». Теперь ошибка говорит,
  что файла нет, и показывает `--project`.

**4.4 выполнена 2026-11-03.** README переписан вокруг бенча сгенерированных кодеков в Node и трёх
браузерах, со сценариями, где JSON лучше. В сьют `generated` добавлены один объект, 500 товаров с
длинным текстом и ряд 100k точек против JSON массивов чисел, на чтение и кодирование. Размер после
сжатия перемерен на сгенерированном кодеке (`bench/node/generated-size.mjs`): таблица фазы 0 была
снята с ручных раскладок, а точки сравнивались с JSON массивом объектов. Что нашлось:
- Геттер поля typed array в цикле `for (...) s.t[i]` стоил в 13–25 раз дороже свойства во всех
  четырёх движках. Исправлено: такие поля одиночного view теперь read-only свойства из
  конструктора. 100k точек в Node и Firefox — 118–137× к JSON, в Chromium и WebKit — 18–22×.
- JSON быстрее: один маленький объект с верификацией в браузерах (0.66–0.94×), 500 товаров с
  текстом и верификацией в Chromium (0.91×), кодирование текста в Chromium (0.88×) и WebKit
  (0.31×).
- Верификация больше чем удваивает чтение текстовых строк (Chromium: 51 → 117 µs).
- После сжатия маленькие ответы на 9–13% больше JSON, ряд float32 не меньше JSON массивов чисел с
  округлёнными значениями (−1…+12%).

Кандидаты в работу: дешевле проверять строки, кодировщик строк для JSC, квантование числовых
колонок (уже в списке после alpha).

**Оптимизации после 4.4, 2026-11-03** ([отчёт](../reports/Оптимизации%20строк%20и%20верификации.md)).
Проверка ASCII-блока словами вместо байтов, без UTF-16 декодера на пустом блоке, без лишнего
`DataView` и спреда лимитов; ASCII-блок от 4 KB кодируется через `encode()` — в JavaScriptCore
`encodeInto` вдвое медленнее. Чтение 500 товаров с верификацией быстрее в 1.4–2.2 раза, в Chromium
теперь 1.64× к JSON вместо 0.91×; кодирование товаров в WebKit — 0.62× к JSON вместо 0.31×, в
Chromium и Node на 6% медленнее прежнего. Не взяты: ручное декодирование маленьких блоков (вызов
`TextDecoder` подешевел до 0.04–0.10 µs), дедуп только коротких строк (теряет back-references
длинных повторов), поиск не-ASCII по склейке (в 2 раза медленнее на смешанном тексте).

### 6.1 Бенчи в GitHub Actions (S)

Сейчас все цифры в доках сняты на одном ноутбуке. Нужно, чтобы у каждой цифры был коммит, дата и
воспроизводимый прогон.
- Отдельный `bench.yml`: `workflow_dispatch` и релизный тег `v*`. Node и Playwright (Chromium,
  Firefox, WebKit на `ubuntu-latest`), сьюты `generated`, `stream-transport`, `middleware`, размеры.
- Shared-раннеры шумят на десятки процентов по абсолютному времени, поэтому основная величина —
  отношение к JSON, снятое в том же джобе подряд. Абсолютные времена публикуются со сноской.
- Результаты — артефакт джоба и данные сайта (`site/src/data/bench.ts`) с коммитом и датой.
- На PR не падать по времени. Максимум — предупреждение, если отношение к JSON просело больше
  допуска (порядка 15–20%) против последнего прогона на `main`.
- Посмотреть инструментированные бенчмарки (CodSpeed и аналоги): считают инструкции, а не время,
  но это V8 под симуляцией, не браузеры. Решить после первого прогона.

**Выход:** таблицы на сайте и в README собираются из прогона CI; повторный прогон на том же
коммите даёт отношения к JSON в пределах ±10%.

**Статус: выполнена 2026-11-04, выход — частично.** [`bench.yml`](../.github/workflows/bench.yml)
гоняет `generated` (10 повторов), `stream-transport` и `middleware`, кладёт результаты в
[`bench/results/ci`](../bench/results/ci), переписывает таблицы README между маркерами
(`bench/readme.mjs`) и пересобирает сайт; цифры скорости на лендинге читаются оттуда же через
`bench/lib/headline.mjs`. `bench/compare.mjs` пишет в summary джоба изменения отношений против
прошлого опубликованного прогона. Что выяснилось:
- Один прогон на рантайм не годится: два прогона на одном коммите разошлись до 2× в Firefox и
  до 60% в WebKit. Поэтому `run.mjs --repeat=n`: каждый повтор в свежем процессе или браузере,
  повторы чередуются между рантаймами, в таблицу идёт медиана отношений.
- С 5 повторами большинство строк сходится в ±10%. Остаток не шум, а две систематические вещи:
  раннеры попадаются на разных CPU (EPYC 7763, 9V74, 9V45), что сдвигает отдельные строки на
  10–25%; несколько строк Firefox бимодальны от запуска к запуску браузера (числовые поля 1000
  юзеров — 28–32× или 64–72× на одном и том же раннере).
- На Linux x64 картина местами другая, чем на M3: Firefox проигрывает JSON на 10 юзерах (0.65× с
  верификацией против 1.48× на M3), а кодирование текста в WebKit и Chromium на уровне JSON, а не
  0.62× и 0.93×. Маленькие ответы в Firefox — кандидат в пул.

### 6.2 GET и HTTP-кэш — обсуждение дизайна

Сначала обсуждение, потом раздел в DESIGN, потом код. Вопросы на обсуждение:
- Какие процедуры идут через GET: явная пометка в роутере, тип-маркер или опция клиента.
- Как вход попадает в URL: base64url бинарного входа, лимиты длины URL, fallback на POST.
- Ключ кэша и `Vary`; `ETag` от хеша ответа, `304` и `If-None-Match`; `Cache-Control` из
  процедуры или мидлвары.
- CSRF: сейчас защита — обязательный `application/vnd.tbr`, у GET тела нет. Только идемпотентные
  процедуры, без побочных эффектов, проверка `Sec-Fetch-Site`.
- CDN и браузерный кэш против клиентского кэша (связь с адаптером TanStack Query).
- Хеш контракта в URL, чтобы кэш не отдал ответ старой схемы после выкатки.

**Выход:** раздел DESIGN с принятыми решениями и списком задач с размерами.

**Статус: выполнена 2026-11-04, сразу с кодом.** [DESIGN §16](DESIGN.md#16-запросы-и-http-кэш),
руководство [guide/queries.md](guide/queries.md). Решения: `query(target, options?)` вместо
JSDoc-тега, вход — бинарный base64url (читаемые параметры не нужны), политика кэша только
статическая. По дороге — контекстная типизация в `use()` (`(_, ctx)` без аннотаций, DESIGN §15):
она убрала главную претензию к DX `query(async (_: void, ctx: Ctx) => …)`. ETag сначала считался
через `crypto.subtle.digest` и делал GET вдвое дороже POST (+15 мкс); синхронный 64-битный хеш
сделал GET дешевле POST.

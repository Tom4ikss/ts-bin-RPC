# Code-first бинарный RPC занимает свободную, но узкую нишу

Ни одно существующее решение не совмещает четыре свойства планируемого проекта: типы берутся из обычных TS-интерфейсов, формат на проводе бинарный, чтение ленивое через представления (views) поверх буфера, числовые данные лежат колонками TypedArray. Популярные TS RPC (tRPC, oRPC, Hono, Elysia) передают JSON. Бинарные TS-first варианты (TSRPC/tsbuffer, Deepkit BSON, Effect `SchemaBinary`, typia protobuf) декодируют всё сразу в обычные JS-объекты. Ленивое чтение в JS есть только у schema-first FlatBuffers и альфа-версии capnp-es. Ниша действительно свободна, но наши замеры и чужие данные сходятся в одном: выигрыш неравномерный. На типичном CRUD при полном чтении он скромный (около 1,5x), а после brotli payload с большим количеством строк проигрывает JSON по размеру примерно на 45%. Решающий выигрыш даёт числовая и колоночная нагрузка (около 300x на декодировании) и частичное чтение больших ответов (2,5–5x). Поэтому проект стоит позиционировать не как «быстрый tRPC для всего», а как типобезопасный транспорт для числовых, колоночных и больших частично читаемых данных, с JSON-режимом для остального. Вторая ценность проекта меньше зависит от формата: если генерировать конкретные типы отдельной CLI, без трансформера компилятора, исчезают главные жалобы пользователей tRPC/Hono/Eden (медленный tsserver, связность монорепозитория, отсутствие версионирования) и главная беда typia и Deepkit (привязка к сборке и к TS 7). Решения, которые нужно принять сейчас, касаются позиционирования, формы поставки (адаптер или собственный фреймворк), идентичности полей и эволюции схемы, политики для строк и верификации, а также модели объектов на клиенте.

## Карта рынка: никто не совмещает code-first, бинарный формат и ленивое чтение

### TS-native RPC: все выводят типы из `typeof router` и передают JSON

Мейнстрим сошёлся на одной архитектуре: клиент импортирует тип сервера, кодогенерации нет, на проводе JSON, валидация через Standard Schema (Zod, Valibot, ArkType). Бинарные TS-first проекты существуют, но остаются маргинальными по адопции и декодируют данные целиком.

| Проект | Откуда типы | Формат на проводе | Ленивое чтение | Адопция / статус (2026-11) | Главные проблемы |
|---|---|---|---|---|---|
| tRPC v11 | `typeof appRouter`, вывод TS | JSON (+superjson), Blob/FormData | нет | 21,9 млн загрузок/мес, активен ([GitHub](https://github.com/trpc/trpc)) | Тормоза TS на больших роутерах: «resolving types … takes 4-8 seconds» ([#5508](https://github.com/trpc/trpc/discussions/5508)). Бинарного тела нет, запросы на него висят годами ([#1937](https://github.com/trpc/trpc/issues/1937)). Версионирования нет ([Skovhus](https://www.skovhus.dev/blog/trpc-auto-versioning)) |
| oRPC 1.x | вывод или контракт `oc` | JSON, сырые бинарные стримы | нет | 7,3 млн/мес, вероятно с транзитивными ([GitHub](https://github.com/middleapi/orpc)) | Та же модель вывода. Бенчмарки собственные: type-check 3000 процедур 1,62 с у oRPC против 2,32 с у tRPC ([orpc.dev](https://orpc.dev/docs/comparison)) |
| Hono RPC (`hc`) | `typeof app` | JSON | нет | часть Hono, 288 млн/мес | Документация прямо пишет: «the more routes you have, the slower your IDE will become» ([Hono RPC](https://hono.dev/docs/guides/rpc)). 600 роутов в одном клиенте уже проблема ([#2976](https://github.com/orgs/honojs/discussions/2976)) |
| Elysia Eden | вывод из приложения | JSON | нет | 1,85 млн/мес | TS2589 при ~90 плагинах ([eden#274](https://github.com/elysiajs/eden/issues/274)), в монорепозитории теряются типы ([eden#110](https://github.com/elysiajs/eden/issues/110)) |
| ts-rest, Zodios | Zod-контракт | JSON | нет | ts-rest в архиве ([README](https://github.com/ts-rest/ts-rest)), последний релиз Zodios в 2023 ([npm](https://registry.npmjs.org/@zodios/core)) | Проекты без бэкера умерли, хотя у них миллионы загрузок |
| Cap'n Web | без схемы | JSON, сознательно ради читаемости в Network tab | нет | Cloudflare ([blog](https://blog.cloudflare.com/capnweb-javascript-rpc-library/)) | Аргументы не валидируются, есть pipelining |
| TSRPC + tsbuffer | TS-типы → `TSBufferSchema` | protobuf-подобный поток тег/длина | нет, рекурсивный eager-декодер | 2,5 тыс./мес ([npm](https://api.npmjs.org/downloads/point/last-month/tsrpc)) | Документация на китайском, один мейнтейнер, монолитный фреймворк ([tsrpc](https://github.com/tsrpc/tsrpc)) |
| Deepkit RPC | TS-трансформер, рантайм-типы | BSON | нет | 9,7 тыс./мес, v1.1.0 вышла 2026-10-31 ([release](https://github.com/marcj/deepkit/releases/tag/v1.1.0)) | Не работает с esbuild/Vite без плагина ([#221](https://github.com/marcj/deepkit/discussions/221)). План по TS 7: «still unclear how» ([#658](https://github.com/marcj/deepkit/issues/658)) |
| Effect RPC + `SchemaBinary` | Effect Schema | бинарный формат из схемы, `fieldId(n)` | нет | Effect v4 ([API](https://effect.website/docs/v4/api/effect/encoding/SchemaBinary)) | Ошибка декодирования одного запроса ломает соединение ([#8826](https://github.com/Effect-TS/effect/issues/8826)), регрессии `toCodec` ([#10178](https://github.com/Effect-TS/effect/issues/10178)) |
| typia protobuf | TS-типы через трансформер | protobuf | нет | typia 15.x | Сложная сборка, ограничения на типы (см. ниже) |

Целевой поиск «code-first TS RPC с ленивыми DataView-аксессорами» не нашёл ни одного проекта ([GitHub topic](https://github.com/topics/flatbuffers)). Ближайшие соседи совпадают с нами только наполовину. У tsbuffer и typia тот же вход (TS-типы), но выход eager и protobuf-подобный. У FlatBuffers тот же стиль выхода, но вход schema-first. Ещё один сигнал 2026 года: **Effect удалил msgpack в пользу `SchemaBinary`** с пронумерованными полями и целыми фиксированной ширины ([livestore#1600](https://github.com/livestorejs/livestore/issues/1600)). Причина была не только в скорости: msgpackr через `new Function()` молча терял сообщения на Cloudflare Workers ([effect#6169](https://github.com/Effect-TS/effect/issues/6169)). Индустрия движется от универсального бинарного формата к бинарному формату, выведенному из схемы.

### Бинарные форматы: ленивые есть только schema-first, и ни один не доказал преимущества над JSON.parse в V8

| Формат / библиотека | Схема | Ленивое чтение в JS | Скорость относительно JSON в JS | Эволюция | Проблемы |
|---|---|---|---|---|---|
| FlatBuffers (`flatc --ts`) | `.fbs` + бинарник `flatc` | да, vtable-офсеты | достоверного бенчмарка нет, в матрице поддержки «?» ([support](https://flatbuffers.dev/support/)). В браузере проигрывает при полной материализации ([Faulkner](https://adamfaulkner.github.io/binary_formats_are_better_than_json_in_browsers.html)) | слоты/`id`, `deprecated`, `flatc --conform` ([evolution](https://flatbuffers.dev/evolution/)) | **Верификатора для JS/TS нет**, строки при каждом обращении декодируются заново, массивы не являются JS-массивами ([HN](https://news.ycombinator.com/item?id=34417310)), есть баги генератора ([#7661](https://github.com/google/flatbuffers/issues/7661)) |
| capnp-es | `.capnp` + `capnpc` | геттеры | данных нет | ординалы | «alpha-quality», нет релизов ([unjs/capnp-es](https://github.com/unjs/capnp-es)) |
| protobuf-es 2.14+ | `.proto` | нет | v2.14 ускорил decode в 1,46–1,99x относительно 2.13 за счёт деревьев замыканий ([release](https://github.com/bufbuild/protobuf-es/releases/tag/v2.14.0)). До этого был на уровне google-protobuf ([adelost](https://github.com/Adelost/javascript-serialization-benchmark)) | `buf breaking` | Бандл ~16 KB gz на один файл ([bundle-size](https://github.com/bufbuild/protobuf-es/blob/main/packages/bundle-size/README.md)) |
| protobufjs | `.proto` | нет | decode 1–3x быстрее JSON, encode 0,2–0,7x | номера полей | CVE-2026-41242: RCE через недоверенные схемы ([GHSA](https://github.com/protobufjs/protobuf.js/security/advisories/GHSA-xq3m-2v4x-88gg)) |
| avsc (Avro) | схема писателя обязательна | нет | encode 8–12x, decode 3–7x, размер 32% от JSON ([adelost](https://github.com/Adelost/javascript-serialization-benchmark)) | по именам, с алиасами ([spec](https://avro.apache.org/docs/1.12.0/specification/#schema-resolution)) | Без схемы писателя данные не прочитать |
| Bebop 2026 | `.bop` | нет | для JS нет независимых данных | теги, структуры заморожены | OrderLarge: 1240 B против 423 B у protobuf ([arXiv](https://arxiv.org/html/2604.09591)) |
| msgpackr / cbor-x | без схемы (records как схема на лету) | `structon`, отделён в 2.0 | с records около 4,7x на Node 15, без них ~1,2x ([msgpackr](https://github.com/kriszyp/msgpackr)). В браузере «among the slowest» ([Faulkner](https://adamfaulkner.github.io/binary_formats_are_better_than_json_in_browsers.html)) | append-only structures | Быстрый путь построен на `eval`. Сжимается хуже JSON (сказано в собственном README) |
| @msgpack/msgpack | без схемы | нет | на Node 22: JSON.parse 340k op/s против decode 280k ([README](https://github.com/msgpack/msgpack-javascript)) | — | Медленнее JSON.parse |

Есть закономерность. Обгоняют JSON.parse те декодеры, которые **генерируют специализированный код под каждый тип**: avsc, protobufjs, msgpackr records, protobuf-es после v2.14. Сам по себе формат на проводе тут вторичен ([protobuf-es v2.14](https://github.com/bufbuild/protobuf-es/releases/tag/v2.14.0)). Для нас из этого следует простое требование: генерировать прямолинейные аксессоры под каждый тип, а не универсальный интерпретатор дескрипторов.

### Кодогенерация из TS-типов: трансформеры проиграли TS 7, отдельные CLI выжили

TypeScript 7 (Go) вышел 8 июля 2026 года **без программного API**. В 7.1 (бета 20 октября 2026) появился новый IPC-API `typescript/sync`/`typescript/async` с запросами к Program и TypeChecker. Трансформеры на стороне emit команда TS считает «out of scope going forward» ([TS 7.0](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/), [TS 7.1 Beta](https://devblogs.microsoft.com/typescript/announcing-typescript-7-1-beta/), [typescript-go#516](https://github.com/microsoft/typescript-go/issues/516)). Классический API TS 6 доступен параллельно через `@typescript/typescript6`.

| Инструмент | Механизм | Состояние на TS 7 | Чему учит |
|---|---|---|---|
| typia / nestia | трансформер, `tags.Type<"uint32">` | Переписан на Go, собственный хост `ttsc`. Первая сборка компилирует Go-плагин «несколько минут» ([dev.to](https://dev.to/nyaomaru/i-compared-6-typescript-validation-libraries-heres-what-surprised-me-325g), [typia#1534](https://github.com/samchon/typia/issues/1534)) | Рантайм отличный (21,9 нс на валидацию против 612 нс у Zod), главная жалоба на интеграцию в сборку |
| Deepkit | трансформер + VM байткода | Остаётся на TS 6, план неясен ([#658](https://github.com/marcj/deepkit/issues/658)) | `type uint32 = number` работает только потому, что трансформер видит имя алиаса |
| ts-json-schema-generator | checker → файл схемы, как наш CLI | Порт на `typescript/sync` оценён в 3–5 недель, плюс экспериментальный Go-порт ([#2199](https://github.com/vega/ts-json-schema-generator/issues/2199)) | Наивный IPC-порт: 535 мс → 1,6–2 с на ~73 тыс. вызовов checker |
| ts-runtime-checks | трансформер через ts-patch | Застрял на TS 5.7 ([GitHub](https://github.com/GoogleFeud/ts-runtime-checks)) | Трансформерный путь тупиковый |
| ts-morph | обёртка над JS API | 28.0 работает на TS 6, для TS 7 пишется форк ([#1621](https://github.com/dsherret/ts-morph/issues/1621)) | Жёстко зависеть от ts-morph не стоит |
| TypeBox, Zod, Effect Schema | схема-билдер → тип | Компилятор не нужен | Альтернатива code-first подходу, но не «обычные интерфейсы» |

Отсюда два вывода. Отдельная CLI, которая **только читает типы** и пишет обычный `.ts`, использует ровно тот read-only срез, который команда TS обещает сохранить. Дешёвый путь миграции выглядит так: TS 6 API за тонким адаптером сейчас, порт на `typescript/sync` после стабилизации 7.1. Кроме того, примитивный алиас `type u32 = number` чекер через обычный API различает ненадёжно (это наш вывод, напрямую не проверен). Пересечение-бренд `number & {…}`, как у typia и Effect `Brand`, чекер видит гарантированно ([typia tags](https://typia.io/docs/validators/tags/), [Effect Brand](https://effect.website/docs/code-style/branded-types/)).

Все зрелые потребители числовых данных (deck.gl, uPlot, GeoArrow, Perspective) требуют **колонок TypedArray** и прямо наказывают за построчные объекты. По словам deck.gl, «99% of the CPU time» обновления буферов уходит на пользовательские аксессоры ([deck.gl perf](https://deck.gl/docs/developer-guide/performance)). Мейнтейнер uPlot критикует форматы вида `[[x,y],…]` ([uPlot](https://github.com/leeoniya/uPlot)). Открытой остаётся четвёрка свойств, которой нет ни у кого: схема из обычных TS-интерфейсов, SoA-раскладка с настоящими TS-типами колонок, RPC-семантика в браузере и JSON-фолбэк в том же контракте.

## Какие проблемы существующих решений решаемы, а какие упираются в физику JS

Проблемы делятся на три класса. Первый класс устраняется архитектурой: кодогенерация вместо вывода типов и отдельная CLI вместо трансформера. Второй класс решается инженерно, но стоит сил: верификатор, отладка, адаптеры. Третий класс упирается в фундаментальные ограничения JS-движков и сжатия, и его можно только смягчить.

| Проблема | У кого | Решаема? | Как |
|---|---|---|---|
| Тормоза tsserver при выводе типов из `typeof router` | tRPC, Hono, Eden | **Да, архитектурно** | Сгенерированный конкретный клиент. Это то же, что официальные обходы tRPC «bake», Hono `hcWithType` и Eden `Treaty.Sign` ([Hono](https://hono.dev/docs/guides/rpc), [tRPC #2448](https://github.com/trpc/trpc/discussions/2448)), только по умолчанию |
| Связность монорепозитория, расхождение версий, path aliases | Hono, Eden | **Да** | Клиент становится отдельным сгенерированным пакетом без импорта серверного кода |
| Нет версионирования для мобильных клиентов | tRPC | **Да** | Lockfile стабильных ID полей, append-only, CI-проверка совместимости в духе `buf breaking` / `flatc --conform` |
| Нет бинарного тела | tRPC (#1937) | **Да** | Кодек как адаптер к существующему RPC |
| Сборка привязана к трансформеру, TS 7 ломает плагины | typia, Deepkit, ts-runtime-checks | **Да, архитектурно** | CLI на TS 6 API, закоммиченный `.ts` на выходе. Пользовательский бандлер ничего не знает о кодогене |
| `eval`/`new Function` в рантайме: CSP, Workers, RCE | msgpackr records, protobufjs | **Да** | Код генерируется на этапе сборки, схемы в рантайме не интерпретируются |
| FlatBuffers TS не проверяет буфер | FlatBuffers | **Да, ценой скорости** | Предварительный проход верификатора или проверяющие геттеры. По нашим замерам это примерно вдвое съедает выигрыш частичного чтения ([zerocopy-bench](../README.md)) |
| Строки декодируются при каждом обращении | FlatBuffers ([HN](https://news.ycombinator.com/item?id=34417310)) | **Да** | Мемоизация при первом чтении. У нас это дало 1,8–3,7x против JSON на повторных чтениях и сортировке |
| Неудобный API: массивы не массивы, `itemsList` | FlatBuffers, google-protobuf | **Да** | Генерировать array-like с итератором, числовые колонки отдавать как настоящие TypedArray |
| int64 > 2^53 | protobuf в JS ([HN](https://news.ycombinator.com/item?id=33381571)) | **Да** | Явная политика: бренды `u64`/`i64` поверх `bigint`, как у typia |
| Сеть непрозрачна в DevTools | все бинарные | **Частично** | CLI `decode`, JSON-режим того же контракта, позже devtools. Deepkit и TSRPC пришлось строить такие инструменты ([deepkit](https://github.com/marcj/deepkit/releases/tag/v1.1.0), [tsrpc-cli](https://github.com/k8w/tsrpc-cli)) |
| Ленивые views не являются POJO и конфликтуют с React Query `structuralSharing`, RSC, `structuredClone` | любой ленивый формат | **Частично** | `toJSON()`/`toObject()`, адаптер TanStack Query с материализацией. Protobuf-es v2 ушёл от классов именно из-за «serialization boundary» ([Connect-ES 2.0](https://buf.build/blog/connect-es-v2)) |
| JSON.parse нативный: один проход, однобайтовые строки, кэш атомов в JSC | всё против JSON | **Нет, только смягчение** | Строки в JS нельзя сделать zero-copy, их обязательно материализовать. При полном чтении потолок около 1,5x. Faulkner показал, что FlatBuffers проигрывает при полной материализации в браузере |
| Бинарный формат сжимается хуже JSON | msgpackr, cbor-x (в своих README), Lucid ([blog](https://lucid.co/techblog/2019/12/06/json-compression-alternative-binary-formats-and-compression-methods)) | **Частично** | Дедупликация строк, группировка байтов по типу, varint там, где не нужен произвольный доступ. Офсеты фиксированной ширины всё равно плохо сжимаются: это цена ленивого доступа |
| Медленный TextDecoder: фиксированная цена вызова, не-ASCII в разы медленнее | V8/Node ([node#61041](https://github.com/nodejs/node/issues/61041)) | **Частично** | Короткие ASCII-строки декодировать JS-циклом, длинные одним вызовом, при полном чтении декодировать весь heap разом |
| WebSocket без backpressure, WebSocketStream есть только в Chromium | транспорт ([caniuse](https://caniuse.com/mdn-api_websocketstream)) | **Частично** | Управление потоком на уровне приложения. WebTransport стал Baseline с Safari 26.4 ([webkit](https://webkit.org/blog/17862/webkit-features-for-safari-26-4/)) |
| SharedArrayBuffer требует COOP/COEP, в Safari нет `credentialless` | worker-сценарии ([web.dev](https://web.dev/articles/cross-origin-isolation-guide)) | **Да, обходом** | Работать на transferable `ArrayBuffer`, без SAB |
| Проекты с одним мейнтейнером умирают | ts-rest, Zodios, TSRPC | **Организационно** | Маленькая поверхность, адаптеры вместо фреймворка, спецификация формата отдельно от кода |
| Не-TS клиенты | все code-first | **Частично, позже** | Экспорт схемы, как `typia.protobuf.message<T>()` ([typia](https://typia.io/docs/protobuf/message/)) |

## Наши замеры совпадают с внешними: числа выигрывают, строки нет

Собственные измерения (Node 22.13, M3 Pro) хорошо ложатся на внешнюю картину ([zerocopy-bench](../README.md)). На полном чтении 1000 пользователей бинарный формат даёт 307 мкс против 469 у JSON, то есть **1,5x**. Чтение 2 из 7 полей даёт **4,6x**, но верификация недоверенного входа срезает это примерно вдвое. Повторное чтение имени с мемоизацией даёт **3,7x**, сортировка **1,8x**. Числовые данные, 100 тыс. точек, читаются за **71 мкс против 22 620**, кодируются за 253 мкс против 31 561. Размер после brotli: **21,4 KB против 14,6 KB** у пользователей (+47%), **1,09 MB против 1,37 MB** у точек (−20%). Шум между прогонами доходит до 20–40%, поэтому мелкие различия значимыми считать нельзя. Браузеры пока не измерены.

Эти цифры нужно читать вместе. Для CRUD-ответа на 1000 записей выигрыш CPU на полном чтении составляет около 160 мкс, а сеть платит лишние ~7 KB сжатого трафика. На мобильной сети 7 KB стоят больше 160 мкс, так что для медианного CRUD-пользователя бинарный формат оказывается **регрессией**, а не улучшением. Это совпадает с давним опытом: Auth0 в браузере получил всего ~4% выигрыша по времени при ~9% меньшем размере ([Auth0](https://auth0.com/blog/beating-json-performance-with-protobuf/)), Lucid показал, что под Brotli-11 JSON почти не уступает бинарным форматам ([Lucid](https://lucid.co/techblog/2019/12/06/json-compression-alternative-binary-formats-and-compression-methods)), а Discord рекомендует JSON для своего gateway ([Discord](https://docs.discord.com/developers/events/gateway)). Есть и обратный довод: при слабых компрессорах (zlib) бинарный формат всё ещё экономит около 20% ([Uber](https://eng.uber.com/trip-data-squeeze-json-encoding-compression/)), а CDN обычно сжимают динамический контент на brotli 4–6, а не 11. Поэтому разрыв в 45% надо перемерить на реальных уровнях сжатия, прежде чем считать его окончательным.

Строковая часть подтверждена со всех сторон. Фиксированная цена вызова TextDecoder (у нас 50–70 нс) объясняет, почему msgpackr декодирует строки короче 32 байт через `String.fromCharCode` ([Kris Zyp](https://kriszyp.medium.com/building-the-fastest-js-de-serializer-a413a2b4fb72)), а protobuf-es добавил ASCII fast path. В Node TextDecoder упирается в конструктор `Utf8DecoderBase` (~50% профиля). Арабский и китайский текст декодируется со скоростью **~0,4 GiB/s против ~19,7 GiB/s для ASCII** ([node#61041](https://github.com/nodejs/node/issues/61041)). Наш вывод о том, что UTF-16 на проводе помогает не-ASCII и вредит ASCII, следует из того, что V8 хранит строки в однобайтовом или двухбайтовом представлении ([v8.dev](https://v8.dev/blog/json-stringify)). Отсюда кодирование, зависящее от содержимого строки. `bundleStrings` у msgpackr (декодировать весь блок строк одним вызовом) обещает 30–50% выигрыша в браузере ([msgpackr](https://github.com/kriszyp/msgpackr)). Это прямой аналог нашего string heap, и он подсказывает режим «декодировать heap целиком, если ожидается полное чтение».

С числами картина противоположная, и здесь у проекта нет серьёзного конкурента. DataView-геттеры в V8 для выровненного little-endian доступа работают «almost the same as TypedArray» ([v8.dev](https://v8.dev/blog/dataview)). SoA-колонка отдаётся без копирования прямо в deck.gl, uPlot или `GPUQueue.writeBuffer`. Сжатие сейчас даёт −20%, но настоящий запас по размеру лежит в квантизации и дельта-кодировании: MLT, колоночный преемник MVT, заявляет до 3x лучшее сжатие за счёт поколоночных кодеков ([MLT](https://arxiv.org/pdf/2508.10791)). Ответов на два вопроса пока нет: как бинарный формат ведёт себя в Safari и Firefox и выдержат ли 300x сравнение с Arrow JS/Flechette, а не с JSON. Без этих данных утверждение «быстрее Arrow» делать нельзя.

## Ядро проекта: кодогенерация, контракт и колонки, а не скорость CRUD

Из всего этого следуют три опорные идеи, упорядоченные по устойчивости.

**Первая идея: code-first контракт с кодогенерацией отдельной CLI.** Это самое защищаемое преимущество, и оно не зависит от формата. Сгенерированные конкретные типы решают проблемы масштаба tRPC/Hono/Eden. Закоммиченный `.ts` решает проблемы сборки typia/Deepkit и переживает TS 7. Lockfile ID полей даёт версионирование, которого нет у tRPC. Даже в JSON-режиме это полезный продукт.

**Вторая идея: SoA-колонки TypedArray с настоящими TS-типами.** Здесь проект закрывает пустую клетку между Arrow (колонки, но рантайм-схема, `any`, 43 KB gz, нет браузерного RPC) и игровыми сериализаторами (дельты, но AoS и привязка к фреймворку). Выигрыш на два порядка измерен и согласуется с тем, чего требуют deck.gl и uPlot.

**Третья идея: ленивые views с мемоизированными строками.** Она даёт 2,5–5x на частичном чтении больших ответов и 1,8–3,7x на повторных чтениях. Это ценно для конкретных сценариев: таблицы, списки, из которых рендерится часть полей, проксирование. На полном чтении маленьких CRUD-ответов выигрыш невелик, а по сети это регрессия.

Отсюда позиционирование: **«типобезопасный бинарный транспорт для числовых, колоночных и больших частично читаемых данных; JSON по умолчанию там, где он лучше, в рамках одного контракта»**. Прецедент такой модели есть в индустрии: у Binance JSON-кадры управления и SBE-кадры данных идут по одному сокету. Чего проект делать не должен: соревноваться с tRPC за типичный CRUD, заменять Arrow в аналитике (лучше дать импорт/экспорт Arrow IPC) и обещать победу над JSON.parse на строках.

Реалистичные конечные цели по этапам выглядят так. **Этап 1**: CLI-кодоген на TS 6 API, кодек (views, SoA, верификатор), lockfile с CI-проверкой, CLI `decode`, HTTP-адаптер плюс адаптер к одному популярному RPC (tRPC link или oRPC serializer), публичная спецификация формата, браузерные бенчмарки против JSON, Arrow JS/Flechette и TSRPC. **Этап 2**: серверный стриминг поверх WebSocket со смешанными кадрами, snapshot + delta для колонок (append-only для временных рядов, разреженные обновления для сущностей), хелпер растущего кольцевого буфера (больная тема uPlot [#1122](https://github.com/leeoniya/uPlot/issues/1122)), квантизация и delta+zigzag для монотонных колонок, бэкенд `typescript/sync` для TS 7.1. **Этап 3**, по спросу: WebTransport, экспорт схемы для не-TS клиентов, interest management, devtools-расширение. Цели вроде «стандарт индустрии» или «замена tRPC» нереалистичны: история ts-rest, Zodios и TSRPC показывает, что даже миллионы загрузок не спасают проект без организационной опоры, а адопцию в этой области определяли DX и интеграции (TanStack Query, Next.js), а не эффективность формата.

## Решения, которые нужно принять сейчас

1. **Основной сценарий и позиционирование.**
   Варианты: (а) универсальная замена JSON-RPC для любого CRUD; (б) нишевый транспорт только для числовых и realtime-данных; (в) гибрид: бинарный формат для числовых, колоночных и больших частично читаемых ответов, JSON для остального, выбор на уровне процедуры.
   Компромиссы: (а) даёт самый широкий рынок, но спорит с замерами: +47% сжатого размера и всего 1,5x на полном чтении, поэтому для медианного пользователя это регрессия. (б) честен по цифрам, но слишком узок, и пользователю нужен второй RPC для остального приложения. (в) сложнее в реализации (два кодека, согласование), зато одна схема покрывает всё приложение.
   **Рекомендация: (в)**, в маркетинге и бенчмарках вести с колонок и частичного чтения. Режим по умолчанию для процедуры выбирать по форме типа: если в типе есть числовые колонки или массивы больше порога, бинарный формат, иначе JSON. Пользователь может переопределить.

2. **Форма поставки: собственный фреймворк или кодек с адаптерами.**
   Варианты: (а) полноценный RPC-фреймворк со своим сервером и клиентом; (б) только кодек и кодоген, интеграция через адаптеры (tRPC link, oRPC serializer, Hono content-type); (в) кодек как ядро, адаптеры к популярным RPC плюс тонкий собственный транспорт для стриминга и колонок, которых у них нет.
   Компромиссы: (а) даёт полный контроль, но TSRPC и Deepkit не взлетели во многом потому, что требовали принять весь фреймворк, а паритет с tRPC (TanStack Query, SSE, батчинг, типизированные ошибки, middleware, OpenAPI, MCP) стоит годы. (б) даёт минимальный порог входа, но адаптеры ограничены моделью хоста: tRPC transformer, например, не работает с CBOR ([#1937](https://github.com/trpc/trpc/issues/1937)), а снапшотов и дельт у хостов нет. (в) требует поддерживать две поверхности.
   **Рекомендация: (в).** Начать с кодека и одного адаптера (oRPC выглядит гибче к бинарным телам, но это надо проверить прототипом), собственный транспорт делать только для стриминга.

3. **Тулчейн анализа типов.**
   Варианты: (а) классический API TS 6 через `@typescript/typescript6` за собственным адаптером «TypeSource»; (б) сразу `typescript/sync` из 7.1; (в) Go-шимы к internals typescript-go, как в ttsc/tsgolint; (г) трансформер компилятора.
   Компромиссы: (а) стабилен и документирован, но в 2027 году потребует порта (ts-json-schema-generator оценил его в 3–5 недель). (б) API ещё в бете, без гарантий стабильности, порты ловят паники Go-сервера между nightly-сборками ([#2199](https://github.com/vega/ts-json-schema-generator/issues/2199)). (в) самый быстрый, но ttsc поддерживает 223 linkname-привязки и перегенерирует их на каждом релизе TS. (г) официально тупик: emit-трансформеры «out of scope».
   **Рекомендация: (а)** с узким адаптером: разрешить экспортированные интерфейсы, перечислить свойства с опциональностью, классифицировать примитив, бренд, массив, union или литерал, получить аргументы типа. Не зависеть от ts-morph. Использовать грубозернистые запросы и кэш по id типа, чтобы порт на IPC-API 7.1 был дешёвым. Выход генератора коммитить в репозиторий.

4. **Нотация числовых типов и поддерживаемое подмножество TS.**
   Варианты нотации: (а) собственные бренды-пересечения `number & { readonly [u32Brand]?: never }` с ключом-символом; (б) голые алиасы `type u32 = number`; (в) только теги typia `tags.Type<"uint32">`; (г) JSDoc-аннотации.
   Компромиссы: (б) выглядит красивее всего, но чекер теряет идентичность примитивного алиаса, и это работает только у Deepkit благодаря трансформеру. (в) даёт совместимость с экосистемой typia, но привязывает к её пакету. (г) хрупко, typia сама отговаривает от тегов в комментариях ([typia tags](https://typia.io/docs/validators/tags/)).
   **Рекомендация: (а)** с символьным опциональным ключом, чтобы бренд не всплывал как поле в `getPropertiesOfType` (как `BrandTypeId` в Effect). Дополнительно принимать `tags.Type<…>` typia как алиас. `u64`/`i64` делать брендами поверх `bigint`. `Date` не поддерживать неявно, а ввести бренд `Timestamp` с явной кодировкой. Discriminated unions поддерживать через литеральный дискриминант, который становится байтом-тегом. Отвергать с понятной ошибкой: `any`/`unknown`, функции, классы с поведением, индексные сигнатуры с union-значениями. Typia protobuf отвергает похожий список ([typia](https://typia.io/docs/protobuf/message/)), и пользователи будут пробовать именно эти углы.

5. **Идентичность полей и эволюция схемы.**
   Варианты: (а) lockfile, который генерирует CLI и который хранит `(Type, field) → id`, append-only; (б) явные ID в коде (`/** @id 3 */` или бренд); (в) позиционная раскладка по порядку объявления; (г) сопоставление по именам со схемой писателя в рукопожатии, как в Avro.
   Компромиссы: (а) не засоряет интерфейсы, но переименование выглядит как удаление плюс добавление, и нужен явный механизм. (б) явно и переживает рефакторинг, но шумно и противоречит идее «обычных интерфейсов». (в) хрупко: перестановка полей ломает совместимость. (г) гибко, но требует передачи схемы и усложняет ленивый доступ.
   **Рекомендация: (а) с элементами (б).** Удалённые поля остаются в lockfile как `retired`, их ID никогда не переиспользуются. Значения по умолчанию тоже фиксируются в lockfile, потому что «отсутствие означает значение по умолчанию из кода» делает его частью контракта ([FlatBuffers](https://flatbuffers.dev/evolution/)). Переименования делать через `@renamedFrom` или команду `rename`. Команда `check` нужна для CI. Таблицы, расширяемые через vtable, сделать поведением по умолчанию. Замороженные struct включать только явно. Для enum требовать нулевое значение «unspecified».

6. **Раскладка на проводе и совместимость.**
   Варианты: (а) байт-совместимость с FlatBuffers, чтобы читать `flatc`-клиентами; (б) собственная раскладка в стиле FlatBuffers, оптимизированная под JS: string heap, флаги ASCII, выравнивание колонок под TypedArray; (в) компактный eager-формат вроде avsc или protobuf.
   Компромиссы: (а) даёт бесплатную межъязыковую совместимость, но связывает руки в вопросах строк, выравнивания SoA и дедупликации, а TS-рантайм FlatBuffers всё равно без верификатора. (б) даёт лучший результат в V8, но не-TS клиенты потребуют отдельной работы. (в) лучше по размеру и полному чтению (avsc: 32% от JSON), но теряется ленивый доступ и zero-copy колонки, то есть ядро проекта.
   **Рекомендация: (б)** с опубликованной спецификацией и версией формата в заголовке. Экспорт в `.fbs` или Arrow-схему для колоночных частей отложить на этап 3. Колонки выравнивать по ширине элемента, чтобы `new Float32Array(buf, off, n)` работал без копирования.

7. **Политика для строк.**
   Варианты: (а) TextDecoder на каждую строку при первом чтении, с мемоизацией; (б) гибрид: JS-цикл для коротких ASCII-строк по флагу кодировщика, TextDecoder для длинных и не-ASCII; (в) декодирование всего heap одним вызовом и нарезка подстрок; (г) UTF-16 на проводе.
   Компромиссы: (а) просто, но фиксированная цена вызова в 50–70 нс доминирует на коротких строках. (б) требует флаг и порог, который надо мерить в каждом браузере: оценки в источниках от 18 до 32 байт. (в) выгодно при полном чтении (у msgpackr `bundleStrings` даёт 30–50%), но убивает ленивость при частичном. (г) ускоряет кириллицу, но раздувает ASCII вдвое на проводе.
   **Рекомендация: (б) по умолчанию плюс (в) как режим view** (`readAll`/подсказка от генератора для процедур, которые всегда читаются целиком). Мемоизировать на уровне view. Дать доступ к сырым байтам для сравнения и хэширования. UTF-16 разрешить как опцию на уровне поля, а не делать глобальным выбором. Пороги откалибровать в Chrome, Safari и Firefox до фиксации формата.

8. **Верификация недоверенного входа.**
   Варианты: (а) без верификации, как FlatBuffers TS; (б) предварительный проход верификатора: границы, офсеты, длины, глубина, UTF-8; (в) проверяющие геттеры; (г) режим выбирается по направлению: клиент→сервер всегда проверяется, сервер→клиент опционально.
   Компромиссы: (а) быстро, но повреждённый вход молча превращается в мусор, а переиспользование офсетов позволяет раздуть короткое сообщение в огромные массивы ([karmem](https://github.com/inkeliz/karmem)). (б) проверяет один раз и делает геттеры чистыми, но по нашим замерам примерно вдвое съедает выигрыш частичного чтения. (в) платит только за то, что прочитано, но цена размазывается по каждому доступу и усложняет JIT. (г) прагматичен, но требует понятной модели доверия.
   **Рекомендация: (б) + (г).** Сервер всегда верифицирует вход. Браузер по умолчанию верифицирует в dev-режиме, в production это опция (данные приходят с собственного сервера по TLS). Лимиты на глубину и размер обязательны всегда. `eval` в рантайме не использовать. Пример Effect учит отдельно: ошибка декодирования одного запроса не должна убивать соединение ([#8826](https://github.com/Effect-TS/effect/issues/8826)), конверт ошибки должен декодироваться независимо от полезной нагрузки.

9. **Модель объектов на клиенте: views или POJO.**
   Варианты: (а) только ленивые views; (б) views плюс сгенерированные `toObject()`/`toJSON()` и адаптер TanStack Query, который материализует данные или отключает `structuralSharing`; (в) eager-декодирование в POJO как альтернативный режим для той же схемы.
   Компромиссы: (а) даёт максимум скорости, но ломает spread, `structuredClone`, RSC-гидрацию, сравнение по значению и devtools, а также удерживает буфер в памяти. (б) немного больше кода, зато безопасный выход есть всегда. (в) удобен, но на полном чтении eager-декодер в JS обычно не лучше JSON.parse, если он не специализирован.
   **Рекомендация: (б).** Числовые колонки отдавать как настоящие TypedArray (они клонируются и передаются в worker). View сделать неизменяемым. Для React дать материализацию на границе кэша.

10. **Размер на проводе, JSON-режим и отладка.**
    Варианты: (а) принять больший размер на строках; (б) JSON-режим того же контракта с выбором на уровне процедуры и согласованием через `Accept`; (в) таблица дедупликации повторяющихся строк (enum-подобные значения, ключи) плюс группировка строковых байтов отдельно от офсетов; (г) zstd со словарями.
    Компромиссы: (а) проще всего, но это регрессия для CRUD. (б) требует второго кодека, зато сразу закрывает проблемы отладки (Network tab), не-TS клиентов и string-heavy ответов. (в) даёт реальный, но ограниченный выигрыш: cbor-x признаёт, что упаковка «generally does not yield as much compaction as standard compression tools». (г) zstd как Content-Encoding стал Baseline только в феврале 2026 ([web-features](https://web-platform-dx.github.io/web-features-explorer/features/zstd)), а Discord отказался от словарей для части сообщений как от не окупающихся ([Discord](https://discord.com/blog/how-discord-reduced-websocket-traffic-by-40-percent)).
    **Рекомендация: (б) обязательно с первого дня, (в) для строковых колонок и enum, (г) не делать.** Плюс CLI `decode` для дампов. Размер мерить на brotli 4–6, а не только на 11.

11. **Транспорт и стриминг.**
    Варианты: (а) только HTTP request/response; (б) HTTP плюс WebSocket со смешанными кадрами: JSON для управления, бинарные для данных; (в) сразу WebTransport с датаграммами для ненадёжных снапшотов.
    Компромиссы: (а) просто, но без стриминга нет realtime-ниши (рабочие частоты там 20 Гц у Colyseus и 50 мс у Binance depth). (б) проверенный паттерн (Binance SBE), но у WebSocket нет входящего backpressure. (в) WebTransport Baseline только с марта 2026 и используется на ~0,002% загрузок страниц, протокол ещё не RFC.
    **Рекомендация: (а) на этапе 1, (б) на этапе 2**, с управлением потоком на уровне приложения и протоколом snapshot + delta + ресинхронизация. Транспорт абстрагировать так, чтобы (в) добавлялся без смены формата. Декодирование должно работать на transferable `ArrayBuffer` в worker без SharedArrayBuffer. Отдельно нужен бенчмарк «1–100 сущностей × 20–60 Гц» против Colyseus (9 B за апдейт одной сущности): в этом режиме важны накладные расходы на сообщение, а не пропускная способность.

## Conclusion

Главный сдвиг понимания касается источника ценности. Он не в том, что бинарный формат быстрее JSON: на типичных строковых данных это либо неправда, либо правда на уровне 1,5x, которые съедает сеть. Ценность в сочетании, которого нет ни у кого: контракт из обычных TS-интерфейсов, сгенерированный отдельной CLI (это одновременно лечит болезни масштаба tRPC и болезни сборки typia/Deepkit), и колонки TypedArray с настоящими типами, которые можно отдавать в GPU, графики и воркеры без копирования. Ленивые views здесь сильная, но вторичная опция. Если строить проект вокруг них как главного обещания, он столкнётся с той же стеной JSON.parse, о которую разбились msgpack в браузере и FlatBuffers при полной материализации.

Самый большой риск не технический. Ниша пуста отчасти потому, что спрос на неё узок, а проекты с одним мейнтейнером в этой области умирают даже при миллионах загрузок. Отсюда практичная стратегия: маленькое ядро (кодоген, кодек, lockfile, верификатор), адаптеры вместо фреймворка, JSON-режим как страховка. Первым внешним доказательством должен стать честный браузерный бенчмарк против Arrow JS/Flechette и Colyseus. Сравнение с JSON для числовой ниши уже выиграно, а убедить целевую аудиторию нужно именно в превосходстве над реальными конкурентами.
